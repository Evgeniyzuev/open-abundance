# Open Abundance Project Memory

Этот документ хранит накопительный контекст проекта: исходную концепцию, продуктовые гипотезы, экономические рассуждения, принятые ограничения, риски и вопросы, которые нельзя терять между итерациями.

Он не является очередью разработки. Конкретные принятые решения находятся в `OPEN_ABUNDANCE_MASTER_PLAN.md`, а реальный статус и единственный текущий шаг — в `MASTER_KANBAN.md`.

## 1. Исходная идея

Abundance — AI-координируемая система, которая помогает людям превращать желания в действия, развивать навыки, создавать ценность, находить людей и возможности, получать доход и усиливать общий результат.

Главная пользовательская формула:

```text
делаю полезные челленджи -> растет Core -> растет ежедневное начисление
-> появляются новые возможности -> результат становится видимым другим
```

Первый опыт не должен выглядеть как универсальный планировщик, криптокошелек или каталог функций. Пользователь сначала видит результаты, выбирает главное желание, получает финансовый сценарий и выполняет одно действие сегодня.

## 2. Целевая первая аудитория

- люди, ищущие дополнительный или основной доход;
- фрилансеры и создатели контента;
- люди в смене деятельности или переходе к самостоятельной работе;
- пользователи, которым нужен понятный путь к финансовой или жизненной цели.

Первая когорта — 20-50 лично приглашенных русскоязычных пользователей. Это управляемая beta с интервью и ручным наблюдением, а не публичный запуск.

## 3. Главный недельный опыт

```text
история результата
-> главное желание
-> финансовый план
-> Today
-> проверяемая Core-награда
-> рост Core и ежедневного начисления
-> публикация результата
-> возврат завтра
-> приглашение после собственного результата
```

До появления достаточного числа реальных историй допускаются демо-кейсы, но они всегда маркируются как `Демо`. Реальные истории разделяются на `Подтверждено системой` и `Проверено вручную`.

## 4. Экономическая гипотеза

### Core

- Core — неснижаемая внутренняя основа пользователя, определяющая уровень и ежедневное начисление.
- Текущая расчетная ставка — `0.0633%` в день.
- Пользователь может направлять часть ежедневного начисления обратно в Core через reinvest.
- Core не выводится обратно в Wallet.
- Прямого лимита баланса Core нет.
- Системная выдача Core через челленджи должна быть полезной, проверяемой и защищенной от Sybil abuse, поскольку новый Core увеличивает будущие начисления.
- После нескольких ознакомительных челленджей награды предполагают подтверждение уникального человека и реально полезный результат для пользователя или системы.

### Wallet

- Wallet — доступный внутренний баланс пользователя.
- Wallet используется для переводов, пользовательских заданий, внутренней торговли и будущего внешнего вывода.
- Wallet может получать не реферальный депозит, а долю ежедневного начисления от Core в соответствии с reinvest пользователя.
- В beta обучающие и первые системные челленджи не дают Wallet-награды.
- Командный процент и возможные поздние реферальные бонусы могут начисляться в Wallet только при достаточном покрытии.

### Вклад основателя и пользователей

- Начальный вклад основателя — ориентировочно `1000 USDT` с последующими пополнениями при необходимости.
- Это не заблокированный Wallet основателя. Средства вносятся через Wallet -> Core, после чего Wallet уменьшается, Core основателя увеличивается, а реальные активы остаются в Treasury.
- Аналогично пользователь может внести средства в Wallet и необратимо направить их в Core для ускорения роста.
- Нельзя считать устное обещание не выводить Wallet резервным механизмом; обязательство уменьшается только после фактической Wallet -> Core операции.

## 5. Резерв и покрытие

Основная внутренняя метрика:

```text
withdrawable_wallet_liability =
  сумма доступных Wallet
  + ожидающие выводы

coverage_ratio =
  подтвержденный баланс treasury-кошельков
  / withdrawable_wallet_liability
```

После Wallet -> Core соответствующая сумма перестает быть Wallet liability. Несколько treasury-кошельков агрегируются в один подтвержденный резерв, но имеют отдельные роли и адреса.

Пользователю beta не требуется показывать coverage ratio, runway или устройство Treasury. Ему нужны Core, Wallet, начисление за день, reinvest, история операций и понятный статус вывода. Финансовое здоровье системы показывается только на внутреннем операционном экране.

### Светофор ликвидности — продуктовая гипотеза

- **Зеленая зона:** покрытие не ниже установленного безопасного порога; вывод отправляется автоматически, только с минимальной сетевой/сервисной комиссией.
- **Желтая зона:** вывод либо идет в прозрачной очереди до одного часа, либо пользователь выбирает срочное исполнение с заранее известной повышенной комиссией.
- **Красная зона:** исполнение допускает очередь до суток либо более дорогой срочный маршрут; новые промо-, реферальные и другие Wallet-бонусы останавливаются.
- Уже начисленный Wallet нельзя задним числом блокировать или уменьшать.
- Точные пороги, комиссии и гарантированные сроки еще не определены и требуют юридической и финансовой проверки.

Комиссия за срочность должна быть известна заранее и отражать реальную стоимость ликвидности. Она не должна превращаться в скрытый запрет вывода.

## 6. Treasury и вывод

Предпочтительная будущая структура:

- cold/multisig treasury для основного резерва;
- ограниченный hot payout wallet для автоматических выплат;
- отдельные escrow-кошельки торговли;
- отдельный учет полученных комиссий/выручки;
- автоматическое пополнение hot wallet по лимитам;
- emergency pause при расхождении ledger, атаке или нарушении заранее определенных условий.

Целевой UX — автоматический вывод без ручного ожидания, кроме времени исполнения и подтверждения транзакции USDT/TON. Перед автоматизацией нужны выбор сети, custody-модель, защита ключей, подтверждение адреса, лимиты, idempotency, обработка failed transactions и применимые проверки пользователей/адресов.

Намерение пилота — реализовывать только операции, которые допустимы без регистрации финансового/криптовалютного провайдера в выбранной юрисдикции, и начинать с частных переводов. Это пока ограничение, а не юридически подтвержденный вывод: хранение средств, систематическая маршрутизация переводов и автоматические выплаты могут регулироваться независимо от названия операции.

## 7. Действия при недостатке ликвидности

Рассматривались следующие направления:

- остановка новых Wallet-наград и акций при недостаточном покрытии;
- прозрачная очередь и заранее определенные режимы срочности;
- повышенные бонусы за добровольный Wallet -> Core;
- челленджи и streak за регулярный reinvest или неиспользование Wallet;
- привлечение дополнительной ликвидности;
- пополнение резерва фактической выручкой от торговли и сервисов;
- распределение резервов по нескольким кошелькам;
- отдельный emergency reserve.

Использование кредитных карт на grace period обсуждалось, но считается рискованным: это дорогой сроковый разрыв и не должно учитываться как резерв.

Стимулы за невывод должны быть добровольными. Вывод не должен отменять уже полученные уровни, сертификаты или ранее начисленные награды.

## 8. Сертификаты навыков

Один из способов создавать полезность и снижать текущие Wallet liabilities — системные сертификаты навыков.

Пример направлений:

- привлечение и активация рефералов;
- производство контента;
- наставничество;
- продажи;
- проектная работа;
- подтвержденная помощь другим участникам.

Сертификат выдается после курса и проверяемого результата: рефералов, просмотров, выручки, завершенных задач или подтверждений участников.

Экономическая операция:

```text
Wallet пользователя уменьшается
-> та же сумма необратимо добавляется в Core
-> пользователь получает непередаваемый проверяемый сертификат
```

Сертификат не является буквально бесплатным: это добровольный reinvest ликвидного Wallet в Core. В интерфейсе операция должна называться честно. Сертификаты разных направлений и уровней могут быть требованиями для доступа к заданиям и челленджам.

Минимальные свойства сертификата: направление, уровень, критерии, доказательства, метод проверки, дата, issuer, verification record, публичная проверка и возможность revoke при обнаружении обмана.

## 9. Торговля и выручка

- Система может рекомендовать товары и услуги, подходящие для исполнения желаний пользователя.
- Продавец может платить системе процент от фактически завершенной продажи.
- Комиссия может включаться только после определенного порога оборота или суммы сделки.
- Возможна символическая комиссия за внутренние P2P/market операции, ориентировочно менее 1%, но точная модель не определена.
- Комиссия не является единственной anti-abuse защитой: нельзя награждать валовый оборот, нужны net-flow checks, уникальные контрагенты и выявление циклических переводов.
- В резерв засчитывается только фактически полученная выручка, а не прогноз GMV.
- Коммерчески мотивированные рекомендации должны быть маркированы; комиссия не должна автоматически покупать первое место в выдаче.

## 10. Идентичность и anti-abuse

- После ознакомительных челленджей системные награды предполагают доказательство уникального человека.
- Рассматриваются документы, биометрия и privacy-preserving proof-of-personhood наподобие World ID.
- Proof-of-personhood помогает против Sybil abuse, но не автоматически заменяет KYC/AML там, где они требуются.
- Для наград и переводов нужны non-self checks, idempotency, replay protection, связанные аккаунты/устройства, циклические переводы и ручной review подозрительных операций.

## 12. Открытые вопросы

- Юрисдикция оператора Abundance и страны первых пользователей.
- Допустимая без лицензии модель custody, частных переводов и автоматических выплат.
- Сеть первой выплаты: USDT/TON, USDT в EVM-сети, USDC через провайдера или другой вариант.
- Точные пороги зеленой, желтой и красной зон.
- Размер минимальной, обычной и срочной комиссии.
- Можно ли гарантировать фиксированную ставку юридически и чем она покрывается в долгом горизонте.
- Правила системной Core-эмиссии и оценка будущих Wallet liabilities.
- Критерии первого полезного челленджа и первых сертификатов.

## 14. Правило ведения memory

- Новая существенная гипотеза, аргумент, ограничение или нерешенный вопрос добавляется сюда.
- После принятия решения его краткая исполнимая формулировка переносится в мастер-план.
- Текущий статус никогда не ведется здесь — только в канбане.
- Устаревшая информация не удаляется молча: она помечается как отмененная или замененная новым решением.
