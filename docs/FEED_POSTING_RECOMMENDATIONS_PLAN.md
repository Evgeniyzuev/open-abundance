# Feed, Posting And Recommendations Plan

План описывает ленту, постинг, автопостинг, рекомендации и формат "Путь героя" в Abundance.

## Идея

Лента Abundance - это соцсеть роста, где главный формат контента - личный путь конкретного человека, подтвержденный системой.

Пользователь делится:

- достижениями;
- целями;
- желаниями и мечтами;
- событиями;
- опытом;
- знаниями;
- инсайтами;
- эмоциями;
- впечатлениями от своего движения;
- ежедневной/недельной/месячной динамикой.

Ключевое отличие от обычных соцсетей: у автора есть системный контекст - уровень, Core, выполненные задания, доходы, публичные желания, история прогресса. Часть фактов подтверждена системой и не может быть подделана пользователем.

## Продуктовые принципы

1. Лента должна усиливать действие, а не уводить в бесконечный скроллинг.
2. Основной герой контента - конкретный человек и его путь.
3. Уровень автора - доказательство системного капитала и дохода внутри Abundance.
4. Автоматические факты и ручной рассказ живут вместе: система дает доказательства, человек добавляет смысл.
5. Пост должен легко превращаться в действие для читателя: подписаться, задать вопрос, скопировать желание, попроситься на обучение, принять похожий челлендж.
6. Динамика важнее единичного поста: день, 30 дней, 365 дней, было/стало, график, слайд-шоу.
7. Система не должна заставлять пользователя раскрывать лишнее: автор сам выбирает, какие собранные данные показать.

## Основные форматы

### 1. Ручной пост

Похож на посты в Instagram/Facebook/Telegram:

- текст;
- картинки;
- слайды;
- короткое видео;
- ссылка на желание, челлендж, достижение или профиль;
- настройка видимости.

Использование:

- история дня;
- мысль/инсайт;
- опыт выполнения задания;
- эмоция после результата;
- обучающий пост;
- вопрос аудитории.

### 2. Короткое видео

Похоже на TikTok/Reels/Shorts, но вокруг прогресса:

- вертикальный формат;
- 15-90 секунд для MVP/ранней версии;
- подпись;
- системный бейдж автора: уровень, Core range или подтвержденный показатель;
- кнопки действий: подписаться, спросить, скопировать желание, принять челлендж.

MVP может не включать загрузку/транскодинг видео, но модель контента должна быть готова.

### 3. Слайды / карусель

Похоже на Instagram carousel:

- 1-10 слайдов;
- фото, скрин, карточка статистики, график, цитата;
- хорошо подходит для "как я сделал", "было/стало", "30 дней пути".

### 4. Системный автопост

Пост собирается из подтвержденных данных Abundance:

- уровень;
- Core;
- рост Core за период;
- Wallet-доходы;
- доход от заданий;
- общий доход;
- расходы;
- выполненные задания;
- streak/активность;
- время в системе;
- публичные желания;
- прогресс по желаниям;
- новые достижения;
- командные показатели, если автор хочет их показать;
- опубликованные инсайты/итоги.

Автор выбирает, какие блоки включить. Система создает единый формат карточки/поста, а пользователь может добавить текст, фото, видео, голос, комментарий или контекст.

### 5. Hero Journey / Путь героя

Серия системных постов превращается в историю:

- 30 дней как слайд-шоу;
- 365 дней как годовой фильм/альбом;
- было/стало;
- график роста Core;
- график доходов;
- карта желаний;
- список выполненных челленджей;
- ключевые инсайты;
- переломные точки;
- публичные цели на следующий период.

Это реалити-формат: читатели видят не только результат, но и процесс.

## UI-модель

### Лента

Мобильный first screen:

- верхний переключатель: `For You`, `Following`, `Team`, `Hero Paths`;
- быстрый composer;
- карточки постов;
- плавающая кнопка создания;
- фильтр формата: все, видео, слайды, автопосты, желания, знания.

Карточка поста:

- автор, аватар, уровень;
- бейдж системного подтверждения, если есть;
- медиа: изображение/карусель/видео/стат-карточка;
- текст/описание;
- связанные сущности: желание, челлендж, достижение;
- CTA: подписаться, спросить совет, скопировать желание, принять похожий челлендж, попроситься на обучение;
- реакции, комментарии, репост/сохранить.

### Composer

Режимы composer:

- `Post` - ручной пост;
- `Story` - короткий визуальный формат;
- `Progress` - системный автопост;
- `Wish` - пост о желании;
- `Lesson` - опыт/знание/инсайт.

Для `Progress`:

1. Пользователь нажимает "Сделать отчет".
2. Система показывает собранные за период данные.
3. Пользователь чекбоксами выбирает, что показать.
4. Пользователь выбирает шаблон: карточка, слайды, график, было/стало.
5. Пользователь добавляет свой текст/медиа.
6. Пользователь публикует или сохраняет черновик.

### Профиль автора

Профиль должен показывать:

- уровень;
- публичные системные бейджи;
- публичные желания;
- путь героя;
- лучшие посты;
- динамику за 30/365 дней;
- опыт/знания автора;
- кнопку подписки;
- кнопку спросить совет;
- кнопку попроситься на обучение/наставничество;
- кнопку вступить в команду или запросить переход, если правила команды разрешают.

### Публичный профиль пользователя

Публичный профиль - это страница пользователя, которую могут открывать другие пользователи из ленты, команды, рекомендаций, комментариев, Direct и списков контактов.

Всегда видимые поля:

- аватар;
- имя;
- уровень.

Эти поля нельзя скрыть, потому что они нужны для узнавания человека, доверия к системным фактам и базовой навигации по социальной части.

Остальные блоки профиля управляются владельцем:

- доходы;
- расходы;
- Core/Wallet-динамика;
- публичные желания;
- достижения;
- системные бейджи;
- командные показатели;
- лучшие посты;
- путь героя;
- статистика активности;
- опыт/знания автора.

Пользователь может вручную добавить:

- описание о себе;
- ссылки на внешние каналы;
- закрепленные фото;
- видео;
- посты личной ленты.

Личная лента профиля строится из `feed_posts` по `author_user_id`, как Instagram-профиль. Для MVP профильные фото и видео не требуют отдельной галереи: они публикуются как посты или медиа внутри постов через `feed_posts` + `feed_post_media`.

### Внешние соцсети и роль Open Abundance

Для MVP с лимитом Supabase/Vercel около 2GB Open Abundance не должен становиться хранилищем чужих фото и видео и не должен конкурировать с TikTok/Instagram/Telegram как еще одна развлекательная соцсеть.

Продуктовая роль:

- внешние соцсети - витрина, охват и публичная дистрибуция;
- Open Abundance - штаб пользователя: цели, желания, ресурсы, Core/Wallet, прогресс, команда, доказательства роста и следующие действия;
- внешний пост внутри Open Abundance получает смысл: к какой цели, дню, желанию, челленджу или результату он относится;
- пост из Open Abundance должен легко превращаться во внешний пост, чтобы пользователю не приходилось вручную пересобирать daily results в каждой соцсети.

MVP-принцип хранения:

- не загружать внешние фото/видео в Supabase Storage;
- хранить только URL, provider, normalized external id, безопасный caption/title, author handle, fetched_at/cache status и связь с `feed_posts`;
- thumbnail хранить только как внешний URL или вообще не хранить, если provider требует live embed;
- official embed грузить только по клику "Показать превью", чтобы не тащить тяжелые third-party scripts в каждую карточку feed;
- если embed недоступен, карточка остается полезной как ссылка + контекст роста в Open Abundance.

Inbound flow: внешний пост -> Open Abundance:

1. Пользователь нажимает "Добавить внешний пост" в feed/blog/profile или у конкретной цели/желания/challenge.
2. Вставляет ссылку на TikTok, Instagram, Telegram или другой поддержанный provider.
3. Сервер нормализует URL, определяет provider и external id.
4. Система создает `feed_posts.post_type = external_link` или связывает внешний источник с существующим постом.
5. Пользователь выбирает контекст: цель, желание, daily progress, challenge, achievement, команда или "просто в блог".
6. Карточка появляется в личном blog и, если `visibility = public`, в общей ленте.
7. В карточке всегда есть возвратные действия внутри Open Abundance: добавить вывод, связать с планом, создать задачу, отправить лидеру, добавить похожее желание, отметить как доказательство прогресса.

Outbound flow: Open Abundance -> внешние соцсети:

1. Система создает draft daily progress/achievement/level up/challenge post внутри Open Abundance.
2. Пользователь выбирает public blocks и видит preview приватности.
3. Система генерирует share package для внешних соцсетей:
   - короткий текст/caption;
   - публичную ссылку на пост/профиль Open Abundance;
   - stat card image позже, если появится генератор изображения;
   - UTM/source marker для возврата;
   - platform-specific text variants для Telegram, Instagram, TikTok.
4. В MVP кнопки экспорта работают через native share/copy:
   - "Скопировать текст";
   - "Скопировать ссылку";
   - "Поделиться";
   - "Открыть Telegram/TikTok/Instagram" без автоматической публикации.
5. После публикации вовне пользователь может вставить ссылку на внешний пост обратно в Open Abundance, и система прикрепит ее как external mirror к исходному OA-посту.
6. В посте Open Abundance показывается блок "Опубликовано вовне" со ссылками на внешние копии.

Retention-механики после перехода во внешнюю соцсеть:

- открывать внешний пост в новой вкладке/приложении, а в Open Abundance оставлять состояние "продолжить шаг";
- после outbound share показывать короткий чеклист: "вставить ссылку на опубликованный пост", "добавить вывод дня", "создать следующий шаг";
- every external link card должна иметь OA-first action, а не только кнопку ухода наружу;
- daily/weekly recap должен собирать не только посты, а прогресс: что пользователь сделал, чему научился, какие ресурсы выросли;
- внешние соцсети приводят внимание, но статус, уровень, Core, команда, желания и verified snapshots остаются в Open Abundance.

Provider policy для MVP:

- TikTok: поддержать link card и lazy official embed/oEmbed, не хранить видео;
- Telegram: поддержать public post widget по конкретной ссылке на пост, не пытаться импортировать весь канал;
- Instagram: в MVP считать link card основным режимом; live embed включать только после отдельной проверки Meta/oEmbed доступа и не делать критической зависимостью;
- unknown provider: показывать generic external link card без embed.

Reference points:

- TikTok Embed Videos: https://developers.tiktok.com/doc/embed-videos
- Telegram Post Widget: https://core.telegram.org/widgets/posts
- oEmbed spec: https://oembed.com/

### Приватность профиля

Уровни видимости для блоков профиля:

- `public` - видно всем пользователям;
- `followers` - видно подписчикам;
- `team` - видно лиду и прямой команде согласно командным правилам;
- `contacts` - видно пользователям из списка контактов;
- `private` - видно только владельцу.

Правила по умолчанию:

- аватар, имя и уровень всегда `public`;
- доходы, расходы, точные суммы Core/Wallet и финансовая динамика скрыты или требуют явного opt-in;
- публичные желания, достижения и бейджи можно показывать по умолчанию, но владелец может сузить видимость;
- системные факты не отдаются как сырые ledger-данные, а показываются только через публичный snapshot/summary;
- preview приватности должен показывать владельцу, что увидят все, подписчики, команда, контакты и сам владелец.

### Hero Path View

Отдельный экран:

- период: 7/30/90/365 дней;
- режим: слайд-шоу, графики, было/стало, таймлайн;
- карточки дней;
- ключевые события;
- публичные желания;
- доходы и расходы, если автор открыл;
- CTA: "Следить за путем", "Добавить похожее желание", "Принять челлендж".

## Автопостинг

### Период

В один автопост собирается статистика за 24 часа. Опубликовать можно после завершения периода в любой момент, история хранится в базе данных.

- отчет покрывает ровно один 24-часовой интервал;
- период считается по времени системы;
- публиковать можно только завершенный период, за который еще не было системного daily progress поста;
- нельзя сделать два системных daily progress поста за один и тот же период;
- пропущенные дни можно опубликовать позже как backfill.

### Источник данных

Система собирает:

- `level`;
- `core_balance`;
- `core_delta`;
- `wallet_income`;
- `task_income`;
- `total_income`;
- `expenses`;
- `tasks_completed`;
- `challenges_completed`;
- `time_in_app`;
- `active_days`;
- `streak`;
- `public_wishes`;
- `wish_progress`;
- `new_achievements`;
- `team_growth`;
- `team_bonus`;
- `manual_reflection`;
- `media_added_by_user`.

Не все данные обязаны быть в MVP. Важно сразу разделить:

- собранные системой факты;
- выбранные автором публичные факты;
- ручной текст/медиа автора.

Обязательные блоки daily progress автопоста:

- автор;
- ссылка на аккаунт/профиль автора;
- уникальный id/handle автора;
- уровень автора и визуальная отметка, если за день был level up;
- период отчета.
- общий доход в Core за завершенный день;
- сила личной команды: сумма уровней прямых участников, у которых автор является лидом.

Daily progress post должен строиться только по полностью завершенному системному дню. День считается завершенным, когда прошел daily job `run_daily_core_and_team_bonus`: начислены проценты от Core и рассчитаны командные бонусы. Для текущего MVP "общий доход в Core" считается как:

```text
total_core_growth = daily_core_accruals.core_amount + sum(team_core_growth_rewards.reward_amount where leader_user_id = author and bonus_date = accrual_date)
```

`daily_rate` и `reinvest_percent` не являются ростом за день, поэтому они не входят в публичный daily growth post. Доход от заданий/challenges и ручные пополнения Core должны войти в `total_core_growth` позже, когда для них появится отдельный daily ledger/audit source; сейчас эти источники нельзя надежно восстановить из существующих таблиц без риска двойного счета.

Опциональные блоки daily progress:

- точная сумма Core;
- прирост Core за период;
- время в системе;
- общий доход;
- доход от процентов Core;
- доход от команды;
- доход от продаж;
- доход от заданий;
- совокупные расходы;
- отдельные покупки;
- опубликованные достижения;
- новые публичные желания;
- исполненные публичные желания;
- выполненные задания;
- выполненные челленджи;
- пользовательский комментарий/рефлексия;
- прикрепленные изображения автора.

### Ежедневные автопубликации

Daily progress post остается базовым системным автопостом. После стабилизации daily growth нужно добавить отдельные daily draft sources, которые пользователь сможет включать или скрывать перед публикацией:

- новые публичные желания за завершенный день;
- исполненные публичные желания за завершенный день;
- расходы внутри системы за завершенный день.

Эти источники должны попадать в автопост только как агрегированные публичные snapshot-блоки. Сырые wish/expense записи не должны раскрываться в feed API без проверки visibility владельца и прав viewer. Для расходов по умолчанию нужен explicit opt-in, потому что это чувствительный финансовый блок.

Daily draft composer должен быть единым местом настройки видимости отдельных блоков перед публикацией: `public` блоки попадают и в общий feed, и в личный blog автора; `private` блоки остаются скрытыми для чужого viewer.

### Подтвержденность

Автопост получает системный бейдж, основанный на записи в централизованном реестре подтвержденных snapshot-данных.

```text
Verified by Abundance
```

Бейдж означает:

- факты из системных блоков взяты из базы;
- verified snapshot записан в реестр и не меняется после публикации;
- автор мог скрыть часть блоков;
- автор мог добавить ручной текст/медиа;
- ручной текст не является системно подтвержденным фактом.

### Шаблоны автопоста

MVP-шаблоны:

- `Daily Progress` - итоги 24 часов;
- `Wish Progress` - движение к желанию;
- `Challenge Done` - выполненный челлендж;
- `Level Up` - новый уровень;
- `Core Growth` - рост Core;
- `Month Recap` - 30 дней.

Будущие шаблоны:

- `Year Movie`;
- `Before / After`;
- `My Method`;
- `Lessons Learned`;
- `Team Growth`;
- `Mentor Case`.

### Разделы

- `For You` - персональная лента.
- `Following` - подписки.
- `Team` - лид, команда, обязательные посты лида.
- `Hero Paths` - длинные публичные пути.
- `Wishes Like Yours` - люди с похожими желаниями.
- `Level Near You` - люди рядом по уровню.
- `Mentors` - авторы, к которым можно попроситься на обучение.
- `Proof Posts` - системно подтвержденные автопосты.

### Анти-паттерны

Не делать:

- бесконечный кликбейт как главный мотив;
- приоритет только по времени просмотра;
- скрытые манипулятивные streak-потери;
- выдачу ручных заявлений за системно подтвержденные факты;
- принудительную публикацию приватных данных.

## Действия из поста

Каждый пост должен вести к действию:

- подписаться;
- сохранить;
- задать вопрос;
- написать в Direct;
- скопировать желание;
- добавить похожее желание;
- принять похожий челлендж;
- попроситься на обучение;
- попроситься в команду;
- открыть путь героя;
- посмотреть графики;
- поделиться наружу.

Особенно важное действие:

```text
Добавить себе такое желание
```

При нажатии:

1. Система открывает форму желания.
2. Предзаполняет название, категорию, примерную стоимость, визуальный референс.
3. Пользователь адаптирует желание под себя.
4. Система может предложить похожие челленджи и людей, которые уже идут по этому пути.

## Канонические решения по user content — 2026-08-01

Первый user-content slice развивает уже существующий feed, а не создаёт вторую социальную подсистему.

Хранение:

- собственные MVP-файлы загружаются в существующий private Supabase Storage bucket `feed-media`; в БД хранятся только path, metadata, ownership, visibility и processing status;
- доступ выдаётся через server-side visibility check и short-lived signed URL; public row сам по себе не раскрывает private/team media;
- изображения сжимаются и получают размеры/thumbnail; видео сначала ограничено короткими файлами или link-only без сложного streaming/transcoding;
- Supabase Storage — MVP-адаптер, а не вечный vendor lock-in. При достижении лимита, проблемах доступности или стоимости media переносится за `media.open-abundance.com` в S3-compatible storage/CDN без изменения post contract;
- внешние TikTok/Instagram/Telegram/YouTube файлы не копируются: хранится URL + metadata + relation `source|mirror`, embed загружается только после действия пользователя.

Порядок социальных действий:

1. ручной текст + first-party image/short video;
2. одна реакция `like` с unique user/post;
3. плоские комментарии с soft-delete, author controls и report; replies появляются позже;
4. repost как новый пост-ссылка на canonical original с optional commentary, без копирования media;
5. Daily Progress и verified result используют те же cards/visibility rules;
6. saves, несколько эмоций, глубокие ветки и full follows graph — после данных MVP.

Repost всегда повторно проверяет доступ к original. Private/team/followers content нельзя раскрыть через repost, notification, counter или external share.

Внешнее распространение: сначала share package (`caption + public OA URL + selected stat blocks`), ручная публикация пользователем и сохранение mirror URL. Official posting APIs добавляются только при доказанном спросе и наличии moderation/permission contract. KPI — onboarding, first result, D1 и activated referrals, а не clicks/shares сами по себе.

До публичного трафика обязательны report, mute/block для критических случаев, rate limits, media limits и moderation queue. Полная премодерация каждого поста для закрытого MVP не требуется.

### Narrative Direction — 2026-07-15

Для demo-историй принят более личный общий нарратив: герой сначала находится в тяжелой точке — нелюбимая работа, выгорание, тревога за семью, ощущение тупика или давно отложенная мечта. Затем он случайно или через знакомого узнает об Abundance: его приглашают, подсказывают или он сам натыкается на проект. Важно, что герой не верит в обещания и не меняет жизнь за один день — сначала пробует из любопытства, делает маленький шаг и наблюдает за собой.

Дальше Abundance появляется в рассказе через опыт героя: он формулирует желание, возвращается к нему в Goals/Notes, выполняет небольшие действия в Today и постепенно замечает, что у него стало больше ясности, опоры и вариантов. Через время возникает личное осознание: «я действительно могу менять свою жизнь». Финал — не рекламное обещание, а субъективное ощущение героя: стало проще принимать решения, выбирать ритм, развивать свое дело, быть рядом с близкими и возвращаться к давним желаниям.

Обязательные правила подачи:

- рассказ от первого лица, с конкретными эмоциями и сомнениями героя;
- Abundance — точка входа и среда для последовательных действий, а не магическая причина успеха;
- сначала любопытство и маленькая проба, затем постепенный накопительный эффект;
- не обещать гарантированный доход, постоянный рост, легкий уход с работы или одинаковый результат для каждого;
- не превращать fictional demo story в отзыв реального пользователя: бейдж `Демо-история` и системная маркировка сохраняются;
- финал может быть теплым и очень хорошим, но герой не обязан выглядеть безупречно счастливым: важнее ощущение свободы, ясности и реального выбора.

### System Story Direction — 2026-07-19

### Отложенная media-инфраструктура

Pinterest hotlink решает текущую проблему доступности, но остается временным внешним источником без контролируемого SLA и гарантии сохранности URL. Целевая архитектура для растущего редакционного и пользовательского медиа:

```text
Open Abundance → media.open-abundance.com → CDN → S3-compatible Object Storage
```

Что потребуется от владельца проекта:

1. Выбрать провайдера, доступного целевой аудитории в России: например Timeweb Cloud S3, Yandex Object Storage или Selectel S3.
2. Создать публичный bucket для редакционных изображений; пользовательские материалы в будущем хранить отдельно с собственными правилами доступа.
3. При необходимости создать поддомен `media.open-abundance.com` и направить его на CDN/storage endpoint.
4. Добавить секреты только в локальное окружение и настройки deployment, не коммитить их:

```text
MEDIA_S3_ENDPOINT=
MEDIA_S3_REGION=
MEDIA_S3_BUCKET=
MEDIA_S3_ACCESS_KEY_ID=
MEDIA_S3_SECRET_ACCESS_KEY=
MEDIA_PUBLIC_BASE_URL=
```

5. Подтвердить допустимый бюджет, лимит хранения и исходящего трафика.
6. После настройки проверить production через российского провайдера.

После этого Codex может реализовать upload pipeline, WebP/AVIF и responsive variants, стабильные content-addressed keys, cache headers, перенос существующих медиа, обновление URL миграцией, сохранение attribution и резервный сценарий смены провайдера.

Рабочая формула поста: «мне было плохо и я не видел выхода → случайно узнал об Abundance → попробовал без больших ожиданий → сделал несколько маленьких шагов → заметил первые изменения в себе и быту → понял, что могу менять направление → сейчас живу проще и ближе к своей мечте».

Первые пять переписанных постов приняты по общей дуге. Следующие пять (`small-town-remote-career`, `designer-second-career`, `teacher-independent-practice`, `maker-to-small-brand`, `local-service-online`) подготовлены в более разговорной редакции: с разным способом знакомства с Abundance, короткими бытовыми фразами и меньшим количеством повторяющихся конструкций «я сделал / я понял». ## Принятые решения

### Daily Progress

1. Период автопоста.
   Решение: один daily progress автопост покрывает ровно 24 часа по времени системы.

2. Публикация.
   Решение: публиковать можно после завершения периода в любой момент. История периодов и snapshot-данных хранится в базе.

3. Дубли.
   Решение: нельзя сделать два системных daily progress поста за один и тот же период.

4. Backfill.
   Решение: пропущенные дни можно опубликовать позже, если snapshot за период сохранен.

5. Обязательные данные.
   Решение: в daily progress всегда есть автор, ссылка на аккаунт/уникальный id, уровень автора и период отчета.

6. Опциональные данные.
   Решение: все остальные показатели автор может убрать из автопоста.

### Публичность Показателей

1. Уровень.
   Решение: уровень показывается всегда.

2. Core.
   Решение: точную сумму Core и прирост Core автор может включить или выключить в настройках автопостинга.

3. Расходы.
   Решение: для MVP автор может включить общую сумму расходов за период в настройках автопостинга.

4. Покупки.
   Решение: позже можно показывать список покупок за период: картинка товара, сумма, ссылка на товар. Категории можно включать/выключать в настройках, отдельные позиции можно выбирать вручную перед публикацией.

### Форматы

1. Видео.
   Решение: в MVP не делаем полноценный видеохостинг. Сначала нужен единый автопост-формат со статистикой как слайд/stat card, плюс прикрепленные картинки и текст автора.

2. Stories.
   Решение: пока не фиксируем исчезающие stories. Системные данные о прогрессе сохраняются в базе в любом случае.

3. Визуальность автопоста.
   Решение: даже MVP-автопост должен быть визуально интересным, а не сухой таблицей.

### Социальные Действия

1. Комментарии.
   Решение: по умолчанию комментировать могут все, автор может ограничить.

2. Счетчики.
   Решение: нужно спланировать по ресурсам просмотры, реакции, комментарии и подписку на автора.

3. Модерация.
   Решение: премодерации публичных автопостов в MVP нет.

### Verified Registry

1. Подтверждение.
   Решение: verified-статус лучше делать не просто бейджем, а ссылкой на централизованный реестр/snapshot, который нельзя незаметно изменить.

2. Бейдж.
   Решение: если пост содержит stat blocks, бейдж/ссылка на verified snapshot не скрывается.

## Варианты Первого Экрана Social

### Вариант A: `For You`

Плюсы:

- сразу дает ощущение живой соцсети;
- быстрее показывает чужие пути и желания;
- лучше для вдохновения и удержания.

Минусы:

- сложнее сделать качественно без хороших рекомендаций;
- новый пользователь может уйти в просмотр вместо действия;
- нужен контроль качества контента.

### Вариант B: Профиль / Мой Путь

Плюсы:

- фокусирует пользователя на собственном прогрессе;
- проще для MVP;
- естественно ведет к daily progress посту.

Минусы:

- слабее ощущение сообщества;
- меньше поводов подписываться и взаимодействовать.

### Вариант C: `Team`

Плюсы:

- подчеркивает связь с лидом и командой;
- хорошо ложится на обязательную подписку на лида;
- меньше шума, больше релевантности.

Минусы:

- у новых пользователей команда может быть пустой или слабой;
- хуже показывает широту возможностей платформы.

### Вариант D: Гибрид

Первый экран состоит из:

- верхняя карточка "Мой путь сегодня";
- 1-2 поста лида/команды;
- 3-5 рекомендованных verified-постов;
- быстрый composer daily progress.

Рекомендуемое направление для MVP: гибрид, потому что он не превращает Social в пассивную ленту и одновременно показывает других людей.

### Данные

- В `progress_snapshots.stats` хранить raw values, display labels и visibility defaults.

- Для расходов хранить минимум два уровня: `expenses_total` и `purchases[]`, где отдельные покупки публикуются только opt-in.

## Проверки

- Публичный профиль всегда показывает аватар, имя и уровень.
- Скрытые доходы, расходы, желания и достижения не попадают в чужой профиль/API.
- Личная лента профиля показывает только посты, доступные текущему viewer.
- Видимость `contacts` работает отдельно от `followers` и `team`.
- Профильные фото и видео отображаются через `feed_posts` + `feed_post_media`, без отдельной MVP-галереи.
- Внешний TikTok/Telegram/Instagram URL создает lightweight post/link card без загрузки внешнего media в Supabase Storage.
- Lazy embed не грузит third-party scripts до действия пользователя "Показать превью".
- Если external embed недоступен, карточка остается доступной как ссылка и сохраняет связь с целью/желанием/прогрессом.
- Daily progress post можно подготовить для внешней публикации через copy/share package без ручной пересборки текста.
- После публикации вовне пользователь может прикрепить внешний URL как mirror к исходному Open Abundance посту.
- Общая лента не показывает private/draft external links другим пользователям.
