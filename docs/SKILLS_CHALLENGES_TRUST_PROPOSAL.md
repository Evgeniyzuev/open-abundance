# Предложение: навыки, обучающие челленджи и Trust v2

Статус: продуктовая гипотеза для обсуждения, 2026-08-01.

Этот документ фиксирует новые идеи до их интеграции в канонические планы и код. Он не меняет текущий порядок `docs/MASTER_KANBAN.md`, не добавляет миграции и не объявляет функции реализованными.

## Короткий вывод

Да, начать с отдельного документа — правильный порядок. Эти функции связаны, но не должны запускаться одним большим релизом:

```text
уровень пользователя и текущий контекст
        ↓
паспорт навыков
        ↓
обучающий челлендж + практический результат
        ↓
проверяемое повышение навыка
        ↓
подбор задач, команда и рынок
        ↓
завершённая сделка
        ↓
Trust v2 с взаимной оценкой
```

Рекомендуемая граница:

- навыки и skill-challenges — отдельный приоритетный слой после стабилизации основного beta-маршрута;
- Trust-lite, уже описанный и частично реализованный, сохраняется как фундамент подтверждённых событий;
- числовая оценка сделки 0.0–5.0 — отдельный Trust v2, только после работающих сделок, отзывов, dispute-flow и анти-накрутки;
- до согласования формул, критериев и видимости не менять `OPEN_ABUNDANCE_MASTER_PLAN.md`, `CHALLENGES_CATALOG.md` и `MASTER_KANBAN.md`.

## 1. Как эти функции вписываются в продукт

Пользователь должен видеть не набор разрозненных рейтингов, а маршрут:

```text
что я умею
→ чему хочу научиться
→ какой маленький результат могу сделать
→ кто проверит результат
→ какие задачи и возможности мне теперь доступны
→ какой подтверждённый результат я создал для другого человека
```

Общие продуктовые правила:

1. Навык — это не самодекларация и не прохождение материала. Уровень навыка повышается только по проверяемому доказательству.
2. Челлендж должен давать личную пользу: результат, портфолио, ясность, связь или доступ к следующему шагу.
3. Core Level ограничивает Skill Level, но Skill Level не заменяет Core Level.
4. Trust — отдельная характеристика надёжности взаимодействий. Он не уменьшает Core, Wallet или уровень пользователя.
5. Количество регистраций, лайков, просмотров и отправленных ссылок само по себе не является достаточным доказательством навыка.
6. Любое числовое влияние на Trust должно быть объяснимым, ограниченным, обратимым через dispute/review и записанным в неизменяемом ledger событий.

## 2. Skills — система навыков пользователей

### 2.1. Что входит в Skill Passport

`Skill Passport` — не резюме и не список желаний, а профиль подтверждённых возможностей пользователя.

Для каждого навыка показываются отдельно:

- название и версия методики оценки;
- текущий уровень;
- статус: `self_declared`, `in_progress`, `verified`, `expired` или `under_review`;
- какие результаты дали уровень;
- ссылки на разрешённые пользователем proof/artifacts;
- дата последнего подтверждения;
- следующий конкретный шаг.

Самодекларация полезна для подбора первых материалов, но не открывает квалифицированные задачи и не даёт Trust.

### 2.2. Начальный каталог навыков

Не следует запускать сразу десятки направлений. Предлагаемый первый каталог:

| Код                     | Название                                                          | Первый проверяемый результат                                                                                 | Тип проверки                                          |
| -------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `vibecoding`             | Vibecoding / создание программных решений с AI | небольшая работающая фича с описанием, git-историей и тестовым сценарием    | обучение + peer review                                   |
| `content_creation`       | Создание контента                                         | опубликованный материал по брифу с корректной маркировкой и измеримым CTA | proof + редакционная проверка                |
| `influence_distribution` | Influence / распространение                                | квалифицированные переходы или активированные участники из контента       | автоматическая метрика + quality gate       |
| `referral_acquisition`   | Привлечение пользователей                         | уникальные активированные рефералы                                                                     | автоматическая серверная проверка |
| `mentoring`              | Наставничество                                              | подтверждённый прогресс участника, которому помогли                                      | progress proof + подтверждение получателя |
| `sales`                  | Продажи и работа с предложением                | завершённая неотменённая сделка с полезным результатом                                | deal ledger + подтверждение                         |

`product_qa`, `project_management`, `community_facilitation` и другие направления можно добавить после проверки первой модели. В первой реализации достаточно `vibecoding` и `referral_acquisition`: они проверяют два разных механизма — экспертную оценку результата и автоматическую метрику.

### 2.3. Уровни навыка

Предлагаемая общая шкала:

| Уровень | Смысл                                                               | Общее требование                                                                                                                                      |
| -------------: | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|              0 | знакомство                                                     | пользователь указал интерес или прошёл вводный материал; это ещё не подтверждённый навык |
|              1 | способен выполнить базовую задачу          | базовый материал, проверка понимания и один принятый небольшой результат                              |
|              2 | стабильно применяет навык                         | несколько результатов или повторяемая серверная метрика с качественным ограничением       |
|              3 | создаёт измеримый результат для других | внешний/командный результат, независимая проверка и отсутствие критических нарушений      |
|             4+ | ведёт сложные задачи и обучает других    | отдельная рубрика направления, более строгий review и подтверждённые результаты во времени  |

Это не универсальные критерии для всех навыков. Для каждого навыка должна существовать собственная `level rubric` с типами proof и порогами.

Инвариант:

```text
earned_skill_level(user, skill) <= user_core_level(user)
effective_skill_level = min(earned_skill_level, user_core_level)
```

Если навык был доказан заранее, а Core Level пользователя позже растёт, навык может автоматически раскрыть уже заработанный уровень. Система не должна повышать Skill Level только потому, что вырос Core Level.

### 2.4. Разные навыки требуют разных доказательств

Нельзя использовать один счётчик для всех направлений.

| Навык                   | Что считать                                                                                                                                             | Что не считать достаточным                     |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Vibecoding                   | принятая работающая фича, тесты, git/proof, peer review                                                                                | количество сообщений AI или строк кода |
| Контент               | качество материала, корректность, согласованный CTA и подтверждённое действие аудитории | только просмотры и лайки                         |
| Influence                    | релевантные переходы, активации и удержание привлечённых людей                                             | массовые клики и спам                               |
| Рефералы             | уникальные активированные рефералы с первым полезным действием                                            | регистрации без активации                      |
| Наставничество | прогресс подопечного, его подтверждение и отсутствие давления                                               | количество отправленных советов          |
| Продажи               | завершённые сделки, отсутствие возврата/спора и оценка результата                                        | объём выставленных объявлений              |

### 2.5. Данные, которые понадобятся позже

Это концептуальная модель, а не инструкция немедленно создавать все таблицы:

- `skills` — каталог навыков, версии rubric и статусы;
- `user_skills` — текущий подтверждённый и раскрытый уровень пользователя;
- `skill_evidence` — неизменяемые ссылки на proof, результат проверки и источник метрики;
- `skill_level_rules` — пороги и требования конкретного навыка;
- `skill_review_requests` — запросы на peer review и их статусы;
- `skill_review_decisions` — структурированные решения проверяющих;
- `skill_progress_events` — история изменения уровня с причиной и idempotency key.

Skill evidence, Trust events и финансовый ledger должны быть разными сущностями. Сделка может быть доказательством навыка продаж, но Trust-изменение не должно напрямую переписывать уровень навыка.

## 3. Челленджи как путь получения навыка

### 3.1. Структура skill-challenge

Каждый обучающий челлендж состоит из трёх слоёв:

1. **Понимание:** короткий материал, инструкция, примеры и проверка ключевых решений.
2. **Практика:** конкретный deliverable, который можно завершить за ограниченное время.
3. **Проверка:** автоматическая, peer review или ручной review с понятной рубрикой.

Карточка челленджа должна содержать:

```text
challenge_id
target_skill
target_skill_level
required_user_level
content_version
personal_result
deliverable
verification_logic
reviewer_requirements
anti_abuse_rules
reward_or_unlock
rework_policy
```

Прохождение материала без результата может открыть следующий учебный блок, но не должно само по себе повышать подтверждённый Skill Level.

### 3.2. Пример: Vibecoding, уровень 1

Предлагаемый маршрут:

1. выбрать рабочую среду из поддерживаемого списка;
2. понять базовые правила работы с актуальными AI-моделями и ограничения их использования;
3. создать или склонировать репозиторий;
4. пройти базовый git-flow: branch, commit, diff, pull/request или эквивалентный review-flow;
5. реализовать небольшую собственную фичу по acceptance criteria;
6. приложить proof: ссылка на результат, описание изменений, тестовый сценарий и известные ограничения;
7. получить три независимые проверки от пользователей с таким же или более высоким уровнем `vibecoding`.

Базовое предложение для peer review: три проверки обязательны, но зачёт — минимум `2 из 3` без критического замечания. Критическое замечание возвращает результат на доработку и не уменьшает Skill Level. Это снижает риск случайного или недобросовестного одного голоса, сохраняя требование трёх независимых проверок.

Проверяющий отвечает не на вопрос «нравится ли работа», а на структурированные вопросы:

- результат запускается или воспроизводится;
- acceptance criteria выполнены;
- proof достаточен;
- есть ли критические проблемы безопасности/данных;
- что нужно улучшить до следующего уровня.

Проверяющий не получает награду за положительный вердикт. Можно дать небольшой нейтральный contribution credit за своевременный качественный review, но он не должен зависеть от оценки `pass`.

Правила независимости:

- нельзя проверять собственную работу;
- один и тот же аккаунт или связанная группа не должна закрывать весь review pool;
- повторные взаимные проверки ограничиваются за период;
- при конфликте интересов проверяющий обязан отказаться;
- критические результаты могут быть дополнительно проверены оператором.

### 3.3. Пример: привлечение рефералов

Материал должен объяснять:

- как поделиться реферальной ссылкой;
- как проверить, что человек действительно зарегистрировался;
- как не обещать гарантированный доход и не давить на человека;
- как рассказывать о системе в интернете с корректной маркировкой;
- какие каналы и форматы допустимы;
- что считать полезным первым результатом приглашённого участника.

Для рефералов нужны два уровня доказательства:

```text
registered_referral (первый уровень навыка)
уникальная не-self referral-связь
→ регистрация и подтверждение аккаунта

quality_referral (следующие уровни)
registered_referral
→ первое полезное действие
→ для части порога — активность около 7 дней
```

Регистрация достаточно для первого уровня навыка, но не для более высоких уровней. Реферальная ссылка без регистрации и дубли связанных аккаунтов не дают прогресса.

Предлагаемые пороги для `referral_acquisition`:

| Skill Level | Активированные рефералы |
| ----------: | --------------------------------------------: |
|           1 |                                             2 |
|           2 |                                             4 |
|           3 |                                             8 |
|           4 |                                            16 |

Это стартовая гипотеза `2^level`, а не окончательная экономика. Порог должен дополнительно учитывать качество активации, abuse-сигналы и лимит нагрузки пользователя. Требование остаётся неизменным: `Skill Level <= Core Level`.

Важно согласовать эту проверку с существующим `Invite a Friend`: текущая проверка `has_referral` слишком слабая для Skill Level и должна быть заменена или дополнена проверкой именно активированных рефералов. Не следует задним числом менять исторические награды без отдельного решения.

### 3.4. Другие направления

Для следующих навыков предварительная логика может быть такой:

- `content_creation`: сначала один материал по брифу и проверка корректности, затем серия материалов с подтверждённым переходом к полезному действию;
- `influence_distribution`: учитывать не охват, а качественные переходы, активации и удержание привлечённых людей;
- `mentoring`: учитывать прогресс конкретных подопечных и подтверждение получателя помощи;
- `sales`: учитывать завершённые неотменённые сделки, качество результата и повторяемость, а не только оборот;
- `project_management`: учитывать принятый deliverable, соблюдение критериев и коммуникацию с участниками.

Точные пороги этих навыков нужно разрабатывать после первых данных по `vibecoding` и `referral_acquisition`.

## 4. Trust: разделение текущего Trust-lite и нового Trust v2

### 4.1. Что уже есть в планах

`docs/TRUST_RECIPROCITY_MARKET_PLAN.md` уже задаёт Trust-lite:

- `trust_events` как журнал подтверждённых событий;
- `mutual_confirmations` как запросы подтверждения;
- `reciprocity_balances` как внутренний сигнал взаимности;
- запрет self-confirmation и повторного фарминга;
- отсутствие публичной числовой репутации в MVP.

Это полезный фундамент для помощи, командных действий, proof и первых сделок. Его не нужно заменять системой оценок.

Предлагаемая пользователем оценка сделки — Trust v2, дополнительный слой над Trust-lite.

### 4.2. Базовый сценарий Trust v2

Оценка доступна только после завершённой сделки:

1. сделка создана и прошла escrow/atomic completion;
2. нет отмены, возврата, chargeback или открытого спора;
3. каждый контрагент один раз оценивает другого по шкале `0.0–5.0` с шагом `0.1`;
4. можно указать структурированную причину и короткий комментарий;
5. событие оценки записывается в отдельный Trust ledger;
6. система рассчитывает изменение Trust пользователя и симметричный 10% эффект для оценивающего;
7. спорная или аномальная оценка проходит review, а исправление делается новой ledger-записью, а не удалением истории.

Оценка 3.0 — нейтральная точка. Оценки выше 3.0 повышают Trust контрагента, ниже 3.0 снижают его. Оценка не должна напрямую менять Core, Wallet, Core Level или уже выданные награды.

### 4.3. Предлагаемая формула, которую нужно откалибровать

Чтобы сумма сделки влияла, но крупная сделка не давала линейного и неограниченного эффекта, можно использовать сглаженный множитель.

Пусть:

- `r` — оценк а от `0.0` до `5.0`;
- `a` — фактически завершённая сумма сделки, а не цена объявления;
- `A` — настраиваемая reference amount для данного рынка/валюты;
- `c` — небольшая константа базового влияния, например `0.25`;
- `β` — калибровочный коэффициент Trust points;
- `L` — уровень оценивающего пользователя.

Кандидат на сырое изменение Trust контрагента:

```text
amount_factor(a) = c + sqrt(clamp(a / A, 0, amount_cap))
raw_delta = β × (r - 3.0) × amount_factor(a)
```

Затем применяется лимит влияния одного оценивающего на одного контрагента:

```text
pair_cap(L) = cap_base + cap_per_level × L
target_delta = clamp_to_remaining_pair_budget(raw_delta, pair_cap(L))
```

Это реализует требование линейной зависимости максимального влияния от уровня пользователя, но не позволяет бесконечно повторять мелкие сделки. Лимит должен быть отдельным для положительного и отрицательного направления и действовать за фиксированный период, например rolling 90 days. Дополнительно нужен лимит на одну сделку и общий rate limit аккаунта.

Эффект для оценивающего:

```text
rater_delta = 0.10 × target_delta
```

Таким образом, положительная оценка полезного взаимодействия слегка повышает Trust обоих участников, а необоснованная негативная оценка имеет небольшую цену для самого оценивающего. Этот эффект также записывается отдельным событием и не может использоваться как единственное доказательство любого навыка.

Критические ограничения формулы:

- `amount_cap` не даёт одной очень крупной сделке определить весь Trust;
- `A`, `β`, `c`, caps и окно должны быть конфигурацией с историей изменений;
- расчёт строится по net settled amount после комиссии/возвратов по единому правилу;
- денежная сумма не должна позволять купить высокий Trust без качественного результата;
- до публичного включения формулу нужно прогнать на исторических и синтетических сценариях.

### 4.4. Видимость Trust

Здесь есть прямое расхождение с текущим мастер-планом: он откладывает сложный публичный Trust/reciprocity score и публичную числовую репутацию.

Предлагаемый порядок:

1. Trust v2 сначала работает в закрытом режиме: ledger, расчёт, admin-анализ и личный приватный summary.
2. Пользователь видит свои оценки, основания, изменения и открытые споры.
3. В профиле контрагента сначала показываются только качественные признаки: подтверждённые сделки, подтверждённые действия, активность во взаимопомощи.
4. Число и место в рейтинге рынка не публикуются, пока не пройдены калибровка и anti-abuse review.
5. После пилота отдельно решается, нужен ли ограниченный публичный диапазон или достаточно качественных бейджей.

Так сохраняются текущие принципы приватности и не появляется ранний публичный рейтинг личности.

### 4.5. Минимальная защита от злоупотреблений

Trust v2 нельзя запускать без следующих правил:

- self-deal, self-rating и связанные аккаунты исключаются;
- одна сторона оценивает одну завершённую сделку один раз, с ограниченным окном редактирования;
- незавершённая, возвращённая или спорная сделка не создаёт финального Trust delta;
- wash trading, круговые сделки и искусственное дробление суммы выявляются отдельно;
- один контрагент не может быстро сформировать весь Trust пользователя;
- низкая оценка требует причины, а экстремальная оценка может требовать evidence или review;
- контрагент может открыть dispute без штрафа за сам факт спора;
- rating нельзя использовать для уменьшения Core, Wallet или пользовательского уровня;
- Trust changes, reviewer decisions и corrections сохраняются как audit trail;
- Trust не должен быть обязательным условием базового доступа к приложению.

## 6. Рекомендуемый приоритет и порядок реализации

Это предложение для следующей ревизии планов. Текущую карточку `MASTER_KANBAN.md` не прерывать.

### Фаза 0. Decision-complete спецификация — сейчас, только документ

Зафиксировать перед кодом:

- начальный каталог навыков;
- общую шкалу и invariant `Skill Level <= Core Level`;
- rubric и proof двух первых навыков;
- определение activated referral;
- правила peer review;
- шкалу Trust, формулу, caps и окно лимитов;
- приватность, dispute-flow и метрики anti-abuse.

### Фаза 1. Skill foundation и Skill Passport — высокий приоритет

Зависимости: существующие пользователь, Core Level, challenge engine и базовый профиль.

Результат:

- пользователь может выбрать интересующие навыки;
- видит Skill Level и следующий шаг;
- self-declared и verified состояния не смешиваются;
- доказательства и история изменений имеют server-authoritative источник;
- пока нет полного каталога курсов и нет публичного рейтинга Trust.

### Фаза 2. Два вертикальных skill-challenge slice — высокий приоритет

Рекомендуемые первые вертикали:

1. `vibecoding` level 1: материал → собственная фича → три peer checks → proof.
2. `referral_acquisition` level 1: материал → корректное приглашение → два activated referrals → автоматическая проверка.

На этом этапе проверяется не объём контента, а весь цикл: принять → учиться → сделать → доказать → получить review → увидеть прогресс.

### Фаза 3. Автоматические уровни и подбор возможностей

Зависимости: минимум один работающий skill-challenge и стабильные server-side proofs.

Добавить:

- пороги уровней 2–3 для первых навыков;
- подбор системных задач по навыкам и Core Level;
- связь с лидерскими задачами, наставничеством и marketplace listings;
- качественные метрики для content, influence, mentoring и sales;
- skill artifacts/certificates только после понятной доказательной базы.

### Фаза 4. Trust v2 foundation — высокий риск, после marketplace completion

Зависимости: `marketplace_deals`, atomic completion, buyer/seller reviews, возвраты, dispute/manual review и anti-abuse telemetry.

Сначала реализовать только:

- сохранение взаимных оценок в закрытом feature flag;
- Trust delta ledger и пересчёт summary;
- pair caps, amount cap, rate limits и audit trail;
- admin calibration report;
- отсутствие влияния на Core, Wallet, Core Level и базовый доступ.

### Фаза 5. Trust v2 ограниченный пилот

Запустить на небольшой закрытой группе и ограниченном числе типов сделок. Публичные числа не показывать. Сначала проверить:

- распределение оценок;
- концентрацию влияния у отдельных аккаунтов;
- частоту споров и возвратов;
- корреляцию оценок с повторными сделками и подтверждёнными результатами;
- возможность накрутки через круговые сделки;
- понятность причин и процедуры dispute.

### Фаза 6. Интеграция в рынок и публичные сигналы

Только после отдельного решения:

- мягкий ranking signal для marketplace;
- качественные бейджи в профиле;
- возможно, ограниченный публичный диапазон Trust без детализации контрагентов;
- расширенные skill certificates и лидерские статусы.

## 7. Предлагаемая вставка в текущий порядок Kanban

С учётом существующего порядка и зависимостей:

1. завершить текущий `Verified Reality Feed`;
2. завершить уже запланированные `Marketplace Deals + Atomic Completion` как инфраструктурный слой, но не включать Trust v2 автоматически;
3. добавить `Skill foundation + Skill Passport`;
4. добавить два вертикальных skill-challenge slice (`vibecoding`, `referral_acquisition`);
5. связать навыки с командным дашбордом и обучающими челленджами лидеров;
6. добавить skill-based matching для задач и предложений;
7. реализовать Trust v2 foundation под feature flag;
8. провести Trust v2 pilot и только затем принимать решение о публичных сигналах.

Почему Trust v2 не должен быть раньше Skills: Trust-оценка сделки отвечает на качество уже состоявшегося взаимодействия, а Skill Passport сначала создаёт понятные критерии того, что пользователь умеет и какие задачи ему можно доверить. Почему Skills не нужно полностью откладывать до marketplace: первые навыки можно доказать через обучение, код, контент и рефералы без финансовой сделки.

## 8. Критерии готовности к интеграции

Документы и код можно начинать менять после согласования следующих решений:

### По Skills

- утверждены первые 2–6 навыков и их названия;
- для каждого первого навыка определены level 1 proof и anti-abuse;
- ясно, что является self-declared, in-progress и verified;
- утверждено правило трёх проверок и порог `2/3` либо выбран другой вариант;
- `activated_referral` согласован с referral/team flow;
- решено, какие данные публичны, командные или private;
- определено, что даёт повышение навыка: доступ, artifact, Core-награда или комбинация.

### По Trust v2

- утверждена шкала Trust points и стартовое значение;
- определены `A`, `β`, `c`, amount cap, per-deal cap, pair cap и окно расчёта;
- подтверждено правило `rater_delta = 10% × target_delta`;
- определены правила для возврата, спора, отмены и частичного исполнения;
- утверждены причины негативной оценки и срок dispute;
- решено, остаётся ли числовой Trust private на первом пилоте;
- есть тестовые сценарии для малой, средней, крупной, повторной и круговой сделки.

## 9. Метрики первого пилота

### Skills и challenges

- доля пользователей, завершивших первый skill-challenge;
- время от принятия до proof и число возвратов на доработку;
- согласованность peer reviews;
- доля ложных pass/fail по ручной выборке;
- activated referral rate вместо простой регистрации;
- доля skill evidence, которую можно воспроизвести;
- влияние Skill Passport на completion технических задач и качество marketplace matching.

### Trust v2

- распределение оценок по сделкам и типам пользователей;
- средний и максимальный Trust delta на пару;
- доля пользователей, достигших pair cap;
- доля оценок с dispute, возвратом или ручным review;
- концентрация положительного/отрицательного влияния;
- выявленные wash/circular trading patterns;
- связь Trust-сигнала с повторными сделками и подтверждённым результатом, а не только с оборотом.

## 10. Зафиксированные ответы и решения для следующей ревизии

Ответы из обсуждения занесены как рабочие продуктовые решения. Они ещё не являются разрешением на реализацию и могут быть уточнены в разделе «Оставшиеся вопросы».

### Skills и peer review

- Каноническое направление называется `software_creation`. `vibecoding` — не отдельный навык, а способ прохождения начальных уровней создания программных решений с AI.
- В первой итерации не проектируем полную шкалу 0–5. Делаем один вертикальный челлендж на первый уровень навыка: инструкции, критерии, практический результат и проверка.
- Уровни навыков визуально показываются в профиле как RPG-параметры персонажа.
- Сертификаты пока откладываются. Они понадобятся позже для поручительства, проверки и допуска к задачам со стороны пользователя с более высоким уровнем навыка.
- Для peer review нужен `peer_point`: проверяемый передаёт peer-point проверяющему перед началом проверки.
- Каждый обучающий челлендж может выдавать один peer-point, чтобы поддерживать предложение проверок.
- Пользователи смогут продавать/покупать peer-points или конкретные проверки, но цена покупки не гарантирует положительный verdict и не заменяет rubric.
- Skill level нельзя получить покупкой peer-points; peer-point подтверждает только факт организованной проверки.

### Привлечение и рефералы

- Для первого уровня навыка `referral_acquisition` базовым результатом считается регистрация привлечённого пользователя.
- Для следующих уровней нужны качественные рефералы: например, часть приглашённых должна сохранять активность семь дней и выполнить первое полезное действие.
- Логика порогов остаётся возрастающей: каждый следующий уровень требует примерно в два раза больше результатов. Значения `2/4/8` — рабочая гипотеза, а не окончательная экономика.
- На ранней стадии не смешиваем простой referral challenge, который может проверять наличие регистрации, и Skill Level: для навыка нужна отдельная версия verification logic.

### Trust

- Trust будет отображаться публичным числом, а не только внутренним ledger или качественным бейджем.
- При регистрации пользователь получает небольшой положительный стартовый Trust. Размер стартового бонуса ещё нужно определить.
- В конце каждого календарного года текущий Trust пользователя умножается на `0.9`. История исходных Trust events не переписывается: применяется версионированный decay в расчёте summary.
- В момент оценки Trust получают оба участника: оцениваемый получает рассчитанное изменение, оценивающий — `10%` от того же подписанного изменения.
- Оценку можно оставить для любого заказа/сделки, включая незавершённую или отменённую, если уже создано взаимодействие с контрагентом. При фактической сумме `0` используется только фиксированная константа Trust.
- Для незавершённых, отменённых и нулевых сделок требуется отдельный тип события и меньший лимит влияния, чтобы сама инициация заказа не стала инструментом накрутки.

### Sales и certificates

- Для первого уровня навыка `sales` достаточно минимальной суммарной выручки от завершённых продаж. Точный порог будет определён отдельно.
- Сертификаты не входят в первую итерацию Skill Passport. Первым результатом должна стать понятная RPG-модель уровней и доказательств в профиле.

## 11. Новые направления 5–9

### 11.1. Автоматизированный вывод Wallet в TON

TON-пополнение уже имеет первый реализованный вертикальный срез: native TON поступает на общий резервный адрес, scanner проверяет finality, а settlement идемпотентно зачисляет Wallet. Следующий финансовый приоритет — автоматизированный вывод Wallet в native TON с того же резервного адреса.

Первая версия:

- только закрытый allowlist;
- пользователь указывает TON-адрес и сумму Wallet;
- сумма сначала резервируется в Wallet;
- worker создаёт и отправляет TON-транзакцию;
- после подтверждения сохраняются сумма, комиссия, курс, network, tx hash и статус;
- при ошибке средства один раз возвращаются в доступный Wallet.

Состояния:

`requested → address_confirmed → funds_reserved → queued → broadcast → confirmed`

Терминальные альтернативы: `cancelled`, `expired`, `failed`, `manual_review`, `refunded`.

Обязательны atomic reserve, idempotency key, лимиты на пользователя/день/общий payout, cooling period после изменения адреса, повторное подтверждение адреса, audit trail, emergency pause и сверка исходящих транзакций. Использование одного адреса для депозита и payout — решение первой версии; долгосрочно лучше разделить основной резерв и ограниченный hot payout wallet. До широкого запуска нужно подтвердить безопасную custody-модель ключа.

Светофор ликвидности сохраняется: green — автоматическое исполнение, yellow — очередь или заранее известная комиссия, red — увеличенная очередь и остановка новых Wallet-обязательств без ретроактивной блокировки уже начисленного Wallet.

### 11.2. Другие криптовалюты и сети

Сначала нужен устойчивый контур `TON native deposit → Wallet → TON withdrawal`. Не подключать много сетей одновременно.

Рекомендуемый порядок:

1. native TON в TON — пополнение и вывод;
2. USDT Jetton в TON — после проверки master contract, wallet address, `transfer_notification`, decimals и finality;
3. одна дополнительная сеть/актив по спросу и операционной готовности;
4. остальные сети — только через общий adapter contract и отдельный risk review.

Для каждой пары `asset + network` отдельно задаются адреса, memo/comment, scanner, finality, price providers, комиссии, минимумы, лимиты, ledger asset code, manual review и правила late/failed/duplicate transaction. Cross-chain bridge и обмен активов — отдельные функции, а не побочный эффект подключения сети.

### 11.3. Пользовательский контент в ленте

Уже есть server-backed feed, системные и ручные посты, verified `Challenge Done`, project reviews и lightweight external links. Внешние фото/видео сейчас не копируются в Storage.

Цель нового слоя:

`пост → подтверждённый контекст → реакция/комментарий/репост → полезное действие читателя`

#### Фото и видео

Собственные файлы хранить в Supabase Storage, не в таблицах. `feed_post_media` хранит post id, object path, mime, size, dimensions, duration, thumbnail, processing status и visibility. Исходник и производные варианты разделяются. Для private/team/followers используются signed URLs и server-side visibility checks. До публичного показа нужны лимиты размера/формата/длительности и scan либо статус `pending_review`. Видео сначала допускается коротким файлом или link-only; сложный transcoding/streaming — позже.

Внешние TikTok/Instagram/Telegram материалы остаются URL + metadata; external media не копируется в Storage MVP; lazy embed включается после действия пользователя. Open Abundance хранит канонический контекст, внешний URL — source или mirror.

#### Комментарии, реакции, репосты

Порядок:

1. `feed_post_reactions` — сначала одна реакция `like` и unique constraint на viewer/post;
2. `feed_comments` — текст, автор, post id, visibility и soft-delete; сначала плоские комментарии или один уровень ответов;
3. `feed_reposts` — ссылка на исходный пост без копирования media, optional commentary;
4. saves, эмоциональные реакции и сложные ветки — позже;
5. report/mute/block/moderation queue — до широкого публичного трафика.

Любое действие повторно проверяет visibility исходного поста. Private/team-пост нельзя раскрыть через repost.

#### Внешние соцсети

Inbound: URL → link card → связь с желанием/челленджем/результатом. Outbound: caption + public link + выбранные stat blocks → пользователь публикует сам → внешний URL сохраняется как `mirror`. Official posting APIs — только после проверки спроса и модерации. KPI — onboarding, первый результат, Day 1 и activated referrals, а не количество ссылок.

### 11.4. Mutual credit и продвижение продавцов

В `docs/MUTUAL_CREDIT_MARKET_PLAN.md` уже зафиксировано:

`mutual_market_balance = total_spent - total_earned`

Цель:

`delta взаимного продвижения → 0
общий легитимный оборот → максимально возможный`

Система мягко продвигает продавцов, которые сами покупают у других, но не штрафует автоматически тех, кто больше продаёт.

Предлагаемый алгоритм:

1. учитывать только completed settlement без возврата/спора;
2. считать spent и earned отдельно по пользователю и rolling window;
3. положительный spent − earned давать как capped boost его активным listings;
4. сглаживать boost, чтобы одна большая покупка не подняла весь каталог;
5. при балансе около нуля постепенно снижать boost;
6. не давать за mutual credit прямые Wallet/Core-награды;
7. исключать self-deal, связанные аккаунты, circular trading, дробление и сделки без deliverable;
8. не показывать balance как публичный рейтинг личности.

`listing_score =
  relevance + freshness + quality/review
  + log(1 + completed_sales)
  + capped_mutual_balance_boost
  - risk/report penalty`

Рекомендации должны учитывать релевантность, unique counterparties, повторное качество, dispute/return rate и концентрацию показов. Включать механику только после marketplace deals, escrow, atomic completion, возвратов и review/dispute слоя.

### 11.5. Future Sim — образ будущего

Future Sim — визуальный сценарий возможного будущего, не гарантия дохода или исполнения желаний. Пользователь видит текущие Core/Wallet/Level, желания и сценарий с множителем `×1000`: дом, машина, впечатления, поездки и будущего Sim с собственной внешностью.

Множитель должен быть явно обозначен как сценарный. Рядом показываются формула, предпосылки и срок; результат нельзя выдавать за реальный баланс, покупку, выплату или доказанный успех.

Этапы:

1. сценарная карточка: расчёт, маршрут и объекты желаний;
2. статичные изображения с добровольным reference-фото/аватаром и watermark `Simulation`;
3. альбом Future Path;
4. видео/интерактивный Sim после проверки стоимости, генерации, модерации и приватности.

Для лица нужны explicit opt-in, private storage, visibility controls, provenance/watermark, удаление по запросу и защита от impersonation. Future Sim — после первого workflow, финансового калькулятора и устойчивого Day 1/3/7; он усиливает retention, но не заменяет реальное действие.

## 12. Первый пользовательский workflow

### 12.1. Цель

`узнал о системе → зарегистрировался → увидел объяснение и истории → сделал небольшие действия → получил первый проверяемый результат → понял Core/Wallet и план → вернулся на следующий день`

Финансовые операции не обязательны для активации. Для allowlist это отдельный добровольный трек.

### 12.2. Day 0

| Шаг | Действие | Результат |
|---:|---|---|
| 1 | onboarding: миссия → системные истории → 20 уровней | понятен общий путь |
| 2 | Google/Email регистрация | аккаунт, Core/Wallet, стартовый receipt |
| 3 | просмотр Abundance System, verified и demo | различены реальные факты и демо |
| 4 | App Testing и отзыв | протестированы разделы, оставлен feedback |
| 5 | одно желание | выбран личный смысл |
| 6 | финансовый план | понятны срок и предпосылки |
| 7 | ежедневная цель по Core | выбран посильный шаг |
| 8 | несколько стартовых челленджей | первый результат и reward receipt |
| 9 | приглашение реферала | после собственного результата |
| 10 | добровольный Wallet-трек | депозит TON, Wallet → Core и малый TON withdrawal для allowlist |
| 11 | итог дня | понятны сделанное и следующий шаг |

Финансовый порядок: объяснить риски → депозит TON → увидеть Wallet → добровольно Wallet → Core → добровольный малый вывод → receipt, комиссия, статус и tx hash. Реальный вывод доступен только при allowlist, покрытии, лимитах и операционной готовности.

### 12.3. Day 1

Показываем:

- текущий Core;
- сумму начисления за день;
- `X × 365` за год и `X × 365 × N` за N лет при тех же предпосылках;
- как рост Core/reinvest меняет будущую дневную сумму;
- сегодняшнее действие для роста Core.

Маленькое первое число нужно объяснить как результат одного дня, а не как разовую выплату. Это расчётный сценарий по действующим правилам, не гарантия начислений «всю жизнь»: формулировка должна учитывать условия системы и возможность только прозрачных будущих изменений.

### 12.4. События и метрики

Нужны server-side события: onboarding/auth completed, system stories viewed, challenge accepted/completed, app review, first wish, financial plan, daily Core goal, referral registered/activated, TON deposit credited, Wallet → Core, TON withdrawal requested/broadcast/confirmed, Day 1 return и first receipt viewed.

Главные метрики: onboarding → registration, registration → wish+plan, registration → first result, first result → referral, first result → Day 1, различение demo/verified, добровольный Wallet-трек, успешность deposit/withdrawal и D1/D3/D7.

## 13. Привлечение первых пользователей

Начинать сейчас, не ожидая полной реализации всех функций. Первые 20–50 человек — закрытая когорта с ручной поддержкой.

| Приоритет | Канал | Метрика |
|---|---|---|
| P0 | founder и тёплая личная сеть | registration → first result |
| P0 | собственные verified/demo истории и Abundance System | view → onboarding |
| P1 | точечный outreach блогерам/создателям | qualified activation |
| P1 | referral после личного результата | activated referrals |
| P1 | тематические сообщества и learning-сессии | completion и D1 |
| P2 | share-пакеты, Telegram/Instagram/YouTube/TikTok link cards, guest posts | onboarding completion |
| P2 | SEO-лендинги | qualified signup |
| P3 | платная реклама | только после retention/coverage quality gates |

Для каждого канала нужен отдельный message/landing и одна измеримая цель. Первый пакет материалов: честное объяснение, что происходит за 24 часа, как работают Core/Wallet, что beta, риски, ссылка регистрации и следующий шаг. Не начинать с гарантированного дохода, массового Wallet-вклада или неконтролируемой рекламы.

## 14. Обновлённый порядок приоритетов

1. **Первый workflow и привлечение** — начать операционно сейчас; закрыть missing events и короткий Day 0/Day 1.
2. **Автоматизированный TON withdrawal** — после стабильного deposit pipeline и до широкого продвижения пополнений.
3. **Базовый пользовательский контент** — media, ручные фото/видео, like, комментарии; затем repost и external share.
4. **Skill Passport + первый software_creation challenge** — RPG-уровень, peer-points, практический результат и peer review.
5. **Marketplace deals/escrow → mutual credit** — сделки, возвраты, reviews, затем net-buyer boost.
6. **Trust v2** — публичное число, взаимное изменение и annual decay после данных по сделкам/anti-abuse.
7. **Другие сети** — сначала USDT Jetton в TON, потом одна следующая сеть.
8. **Future Sim** — после устойчивого workflow и Day 1/3/7.

Операционное привлечение идёт параллельно. В коде одновременно остаётся одна главная Kanban-карточка.
