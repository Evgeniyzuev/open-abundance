# Единый AI-контекст и память пользователя

## Статус

Архитектурное решение, принятое 2026-07-22. Реализация общего context broker, разрешений и долговременной AI-памяти ещё не начата.

Сейчас AI-функции изолированы:

- `/api/ai/chat` получает историю текущего чата и статическую базу знаний `lib/ai/knowledge.ts`;
- чат не получает `profile`, `core`, `wallet`, желания, задачи или заметки пользователя;
- история чата хранится только в состоянии `AiChatApp` и исчезает после перезагрузки;
- `/api/ai/reflections/step` получает только явно выбранную запись, guided-выборы и ответы текущего разбора;
- `Home` получает `profile/core/wallet` через `/api/user/context`, но эти данные не передаются AI.

До появления consent-контракта нельзя незаметно объединять эти потоки или передавать внешнему провайдеру дополнительные личные данные.

## Цель

Каждый AI-вызов должен собираться из общей основы и минимального контекста конкретной функции:

```text
общие правила и знания продукта
        + разрешённый контекст пользователя
        + подтверждённая память
        + контекст функции
        + выбранный пользователем объект и текущий запрос
```

Один AI может помогать во всём приложении, но ни одна функция не получает все данные автоматически.

## Слои контекста

### 1. Общий системный контекст

- роль AI в Open Abundance;
- актуальные механики продукта;
- общие правила безопасности, приватности и человеческого контроля;
- язык, формат ответа и запрет на действия от имени пользователя;
- версия системного prompt и базы знаний.

Этот слой един для чата, Home, разборов, Wishes, Checks и будущих функций.

### 2. Контекст функции

Каждая capability добавляет только свои инструкции и allowlist данных.

| Capability | Разрешённый task-context | Не подключается по умолчанию |
|---|---|---|
| `chat.general` | текущая переписка, общая память и разрешённые цели | дневник, private social, подробные финансы |
| `home.next_action` | текущий Home snapshot, главное желание, Today, разрешённая сводка Core | сырые заметки и история разборов |
| `reflection.process` | одна выбранная запись, выборы и ответы сессии | Wallet, feed, другие заметки и разборы |
| `wish.plan` | выбранное желание, сроки, разрешённые ресурсы | несвязанные желания и личные сообщения |
| `task.plan` | выбранная задача, дедлайн, связанные ресурсы | весь дневник и социальный граф |
| `social.draft` | выбранный черновик и публичная часть профиля | private goals, reflections и финансовые операции |

### 3. Контекст текущего объекта

Это запись, желание, задача, расчёт или черновик, с которым пользователь прямо сейчас работает. Локальные объекты из IndexedDB отправляются только после явного действия пользователя.

### 4. Контекст пользователя

Данные делятся на независимые scopes. Разрешение на один scope не открывает остальные.

- `profile.public` — имя, публичное описание, опубликованные результаты;
- `profile.private` — персональные настройки и непубличные поля профиля;
- `wishes.public` и `wishes.private`;
- `tasks.selected` и `tasks.history`;
- `reflections.selected` и отдельно `reflections.history`;
- `finance.summary` — уровень, агрегированный Core/Wallet и параметры плана;
- `finance.transactions` — операции и переводы, наиболее ограниченный scope;
- `social.public`, `social.private`, `direct_messages`;
- `memory.confirmed` — подтверждённые пользователем элементы AI-памяти.

Публичность внутри приложения не означает автоматического согласия на передачу данных внешнему AI-провайдеру. Первая такая передача всё равно должна быть понятно раскрыта пользователю.

### Quality-gate и wellbeing-контекст

Daily check-in хранится как чувствительный личный сигнал, а не как рейтинг и не как медицинская запись. Одного отрицательного ответа недостаточно для изменения маршрута. Для адаптации нагрузки можно использовать только минимально необходимую текущую сводку и подтверждённую пользователем тенденцию.

Независимо от wellbeing-сигналов Core остаётся строго неснижаемым: AI и quality-gate не могут инициировать его списание, redemption или иное уменьшение.

Сырые ответы, кризисные формулировки и автоматические выводы о диагнозах нельзя сохранять в AI memory автоматически. Wellbeing check-in по умолчанию относится к private-контексту и не передаётся лидеру, команде или общему AI-слою; в общий слой могут попадать только обезличенные агрегаты при отдельном согласии пользователя.

## Разрешения

Для каждого scope хранится один из режимов:

- `denied` — не использовать;
- `ask_each_time` — показывать состав данных перед каждым использованием;
- `session` — разрешено до завершения текущей сессии;
- `always` — разрешено для перечисленных capabilities до отзыва;
- `local_only` — можно использовать локальной логикой, но нельзя отправлять внешнему провайдеру.

Разрешение включает:

- scope;
- список capabilities;
- цель использования;
- срок действия;
- версию privacy-текста;
- дату выдачи и отзыва.

Перед AI-вызовом интерфейс должен уметь показать компактный блок `ИИ получит`: конкретную запись, выбранные поля профиля, финансовую сводку и используемые элементы памяти. Пользователь может убрать любой необязательный источник.

## Долговременная память

Память — не полный архив чатов и не скрытый профиль пользователя. По умолчанию AI может только предложить сохранить короткий memory candidate, а пользователь подтверждает его.

Допустимые типы:

- устойчивая цель;
- предпочтение;
- ограничение или доступный ресурс;
- принятое решение;
- обещанный следующий шаг;
- важный человек или роль, если пользователь явно разрешил;
- стабильный факт, полезный для будущих функций.

Каждый memory item содержит:

- короткую формулировку;
- тип и sensitivity level;
- источник и capability, где он возник;
- `confirmedByUser`;
- дату создания, последнего использования и срок актуальности;
- статус `active`, `superseded` или `deleted`;
- ссылку на заменяющий элемент при изменении решения.

Не сохраняются автоматически:

- сырые reflection-записи и кризисные формулировки;
- диагнозы, предполагаемые скрытые причины и чувствительные выводы AI;
- полные переписки;
- пароли, токены, платёжные реквизиты;
- подробные финансовые операции;
- данные других людей из private-контекста.

Пользователю нужен экран `Память ИИ`: посмотреть, исправить, удалить, экспортировать, временно отключить и полностью очистить память.

## Контракт запроса

Общий серверный тип должен выглядеть концептуально так:

```ts
type AiContextEnvelope = {
  schemaVersion: 1;
  capability: AiCapability;
  locale: "ru" | "en";
  conversation?: AiMessage[];
  selectedObject?: LocalContextItem;
  requestedScopes: AiDataScope[];
  consentSnapshot: AiConsentSnapshot;
  contextItems: AiContextItem[];
  memoryItems: AiMemoryItem[];
  functionInput: unknown;
};
```

Каждый `AiContextItem` имеет `source`, `scope`, `visibility`, `sensitivity`, `updatedAt` и короткое нормализованное содержимое. Провайдер не должен получать внутренние идентификаторы, если они не нужны задаче.

## Компоненты реализации

### `AI Gateway`

Единая точка для Gemini/Groq fallback, таймаутов, JSON validation, streaming, safety и метаданных использования. Функциональные endpoints остаются отдельными, но вызывают общий gateway.

### `Context Broker`

Серверный сборщик, который:

1. проверяет пользователя и capability;
2. загружает актуальные разрешения;
3. пересекает requested scopes с allowlist функции;
4. получает только необходимые server-backed данные;
5. принимает явно выбранные local-first данные от клиента;
6. удаляет лишние поля и ограничивает размер;
7. добавляет релевантную подтверждённую память;
8. возвращает готовый context envelope для AI Gateway.

### `Function Context Registry`

Версионированный реестр описывает для каждой capability:

- системную инструкцию;
- разрешённые scopes;
- обязательные и запрещённые источники;
- token budget;
- response schema;
- safety policy;
- может ли функция предлагать запись в память.

### `Memory Service`

Создаёт candidates, подтверждает, изменяет, отзывает и выбирает только релевантные элементы памяти. Запись в память отделена от обычного AI-ответа.

## Предлагаемые серверные таблицы

### `ai_consent_preferences`

`user_id`, `scope`, `grant_mode`, `capabilities`, `purpose`, `privacy_version`, `expires_at`, `granted_at`, `revoked_at`, timestamps.

### `ai_memory_items`

`id`, `user_id`, `kind`, `content`, `sensitivity`, `source_capability`, opaque `source_id`, `confirmed_by_user`, `status`, `expires_at`, `last_used_at`, timestamps.

### `ai_context_access_log`

Только metadata: `user_id`, capability, использованные scopes, количество context/memory items, provider, latency, status и timestamp. Без prompt, сообщений, reflection-текста и содержимого памяти.

Все таблицы закрыты RLS. Пользователь управляет только своими разрешениями и памятью; чтение для AI-вызова выполняется проверенным server-side кодом.

## Как это работает для конкретного пользователя

### Идентичность

У каждого AI-вызова есть ровно один owner context:

- для guest — локальный `guestId`; разрешения, candidates и подтверждённая память хранятся только на устройстве;
- для registered user — подтверждённый Supabase `user.id`; серверные разрешения и память выбираются только по этому `user_id` под RLS;
- после регистрации guest-память не переносится автоматически: пользователь видит список и отдельно подтверждает импорт;
- context одного пользователя никогда не используется для персонализации ответа другому пользователю.

Публичные данные другого человека могут попасть в AI-вызов только как явно выбранный публичный объект, например опубликованное желание. Они не становятся частью памяти текущего пользователя без отдельного подтверждения и не открывают private context владельца.

### Один AI-вызов

1. Пользователь запускает capability, например `home.next_action` или `reflection.process`.
2. Клиент формирует список необходимых scopes и выбранных local-first объектов.
3. UI сравнивает запрос с разрешениями этого пользователя и при необходимости показывает `ИИ получит`.
4. Пользователь разрешает, исключает необязательные источники или отменяет вызов.
5. Сервер проверяет access token и получает `user.id`; доверять `userId` из тела запроса нельзя.
6. Context Broker пересекает consent пользователя, allowlist capability и реально запрошенные scopes.
7. Server-backed providers загружают только строки этого пользователя и только нужные поля.
8. Клиент добавляет явно выбранные локальные данные; сервер не может запрашивать остальные записи IndexedDB.
9. Memory Service выбирает несколько релевантных `active` items этого пользователя из `memory.confirmed`.
10. AI Gateway получает минимальный envelope, вызывает провайдера и пишет только metadata access log.
11. Если ответ содержит memory candidate, он показывается пользователю отдельно и не сохраняется до подтверждения.

### Карта AI-доступа пользователя

В настройках нужен экран с тремя независимыми блоками:

1. **Данные:** scopes и режим доступа для каждой capability.
2. **Память:** все подтверждённые элементы, их источники, последнее использование и срок актуальности.
3. **История доступа:** дата, функция и категории использованных данных без prompt-текста.

Пример:

```text
Home helper
  profile.public       always
  wishes.private       ask_each_time
  finance.summary      session
  reflections.history  denied
  memory.confirmed     always

Reflection
  reflections.selected ask_each_time
  memory.confirmed     denied
  finance.summary      denied
```

### Изменение и отзыв

- изменение scope применяется со следующего AI-вызова;
- `denied` исключает источник из Context Broker, но само исходное пользовательское данное остаётся в принадлежащем ему продукте;
- удаление memory item исключает его из retrieval немедленно и создаёт metadata-событие удаления без копии содержимого;
- `Очистить память ИИ` удаляет все memory items пользователя, но не удаляет Wishes, Tasks, профиль или другие исходные данные;
- удаление исходного объекта делает связанные memory candidates устаревшими; подтверждённая память либо удаляется, либо требует повторного подтверждения согласно выбранной retention policy;
- отзыв разрешения не может удалить уже обработанный внешний provider request, поэтому disclosure до отправки обязателен.

### Несколько устройств

- guest-память относится только к конкретному устройству;
- registered memory и постоянные consent preferences синхронизируются через сервер;
- разрешения `session` не синхронизируются и заканчиваются на устройстве, где были выданы;
- локальные Notes/Checks/Reflections не появляются на другом устройстве и в AI context, пока для них не реализован отдельный sync/import flow;
- конфликт memory items разрешается через `updated_at` и `superseded`, без молчаливого объединения разных формулировок.

## Local-first данные

Notes, Checks и Reflection Inbox остаются в `open-abundance-offline`. Context Broker не может и не должен читать IndexedDB скрытно. Клиент отправляет только выбранный объект или явно подтверждённую подборку. Разрешение `reflections.history` не должно автоматически синхронизировать дневник на сервер: это отдельное продуктово-приватностное решение.

## Ограничение контекста

Даже при полном разрешении AI не получает всё сразу. Порядок отбора:

1. safety и инструкции capability;
2. текущий объект и запрос;
3. актуальные подтверждённые цели и ограничения;
4. релевантная память;
5. минимальная server-backed сводка;
6. более старые данные только при явной необходимости.

При конфликте источников более свежий подтверждённый элемент имеет приоритет. AI обязан обозначить неизвестность, а не заполнять пробел догадкой.

## Этапы внедрения

1. **Общий фундамент:** вынести provider fallback, базовые правила и типы capability в AI Gateway/Registry без подключения новых пользовательских данных.
2. **Consent UI:** scopes, режимы разрешения и предварительный просмотр `ИИ получит`.
3. **Context Broker:** подключить публичный профиль, выбранное желание и агрегированную Home-сводку.
4. **Function migration:** перевести chat, Home helper и reflection endpoint на единый envelope, сохранив строгий allowlist Reflection.
5. **Подтверждаемая память:** candidates, экран управления и использование только `memory.confirmed`.
6. **Расширение scopes:** private wishes/tasks и финансовая сводка; transaction history, direct messages и reflection history остаются последними и требуют отдельного решения.

## Критерии приёмки

- один и тот же базовый контекст и версия правил используются всеми AI-функциями;
- каждая capability имеет отдельный allowlist и response contract;
- без разрешения личные данные не попадают в prompt или внешний provider request;
- пользователь видит, какие источники будут использованы, и может исключить необязательные;
- local-first данные передаются только при явном выборе;
- память создаётся только после подтверждения и полностью управляется пользователем;
- отзыв разрешения действует на следующий AI-вызов;
- access log не содержит пользовательского текста;
- Reflection не получает финансовые, социальные или другие дневниковые данные по умолчанию;
- удаление memory item исключает его из всех последующих функций.

## Открытые решения

- хранить ли подтверждённую память только локально для guest и синхронизировать после регистрации;
- нужен ли отдельный режим `разрешить один раз` помимо `ask_each_time`;
- какие поля входят в безопасную `finance.summary`;
- разрешать ли AI предлагать память после Reflection или полностью запретить это для дневника;
- срок жизни целей, ограничений и обещанных действий;
- нужен ли отдельный локальный/on-device слой для наиболее чувствительных данных.
