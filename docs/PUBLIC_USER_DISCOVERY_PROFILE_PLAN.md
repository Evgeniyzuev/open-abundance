# Public User Discovery And Profile Plan

Документ описывает, как в Open Abundance должны выглядеть поиск людей, список пользователей, публичная страница, публичные статы и связь страницы с блогом. Он дополняет `FEED_POSTING_RECOMMENDATIONS_PLAN.md`, `REFERRALS_TEAMS_PLAN.md`, `TRUST_RECIPROCITY_MARKET_PLAN.md` и `OPEN_ABUNDANCE_MASTER_PLAN.md`.

## Цель

Пользователь должен быстро находить других людей по понятным критериям, открывать их публичные страницы, понимать уровень доверия и роста, переходить в блог и обратно без ощущения, что лента, профиль, команда, маркет и личные настройки смешаны в одну кучу.

Важная идея: это не просто "каталог аккаунтов". Это социальная карта роста, где каждый человек представлен как участник системы с публично разрешенными фактами: `Level`, `Trust`, `Team`, `Influence`, публичные желания, посты, достижения, опыт и связи.

Дополнительная продуктовая формулировка: каждый пользователь в Open Abundance ведет себя как Telegram-канал со своим контентом, но без отдельной сущности "канал" в MVP. Публичная страница - это профиль + блог + предложения + разрешенные системные факты.

## Decisions 2026-06-12

- `People` живет в `Social -> People`.
- `People` отделен от `Teams`: `People` нужен для поиска и открытия людей, `Teams` - для инструментов взаимодействия со своей командой.
- `Level` всегда публичный и не скрывается настройками видимости.
- `Trust` в MVP строится из уже реализуемой Trust-lite основы: `trust_events`, `mutual_confirmations`, `reciprocity_balances`. В публичном People/Profile показываем summary/бейджи, а не сырой публичный рейтинг личности.
- `Team` для discovery означает силу личной команды: рекомендуемый показатель - сумма уровней прямых участников личной команды. Простое количество участников можно показывать вторым, но оно слабее отражает качество команды.
- `Influence` пока остается planned. На показатель позже влияют просмотры, комментарии, реакции/сохранения, активность блога и особенно количество привлеченных рефералов.
- Написать в личку в MVP можно любому пользователю. Позже добавляются настройки, кто может писать.
- Добавление в контакты - это личная телефонная книга viewer. Добавленный пользователь ничего не подтверждает и ни к чему не обязывается.
- В UI показываем `display_name`. Для URL `display_name` не используем как идентификатор, потому что он не уникален и может меняться.
- MVP-фильтры: `Search`, `Team`, `Referrals`, `Same Level`, `Nearby Level`. `All` не должен означать бесконечный список всех пользователей без ограничений.

## Продуктовые принципы

1. Сначала человек, потом контент.
   В списке и профиле главным объектом является пользователь: имя, аватар, уровень, короткий контекст, публичные статы и действие.

2. Публичное не значит полное.
   Личный профиль владельца может содержать все данные, но чужой viewer видит только то, что разрешено настройками видимости.

3. Поиск должен помогать действию.
   Человек ищет не "кого-нибудь", а наставника, партнера, участника команды, автора полезного блога, продавца услуги, человека с похожей целью или подтвержденным опытом.

4. Переходы должны быть короткими.
   Из строки пользователя можно открыть публичную страницу. Из публичной страницы можно открыть блог. Из поста в блоге можно вернуться к автору. Из команды или маркета можно открыть того же автора.

5. Вид должен быть чистым.
   Нельзя складывать профиль, блог, сделки, команду, кошелек и настройки в один длинный экран. У публичной страницы есть ясные блоки, вкладки и приоритеты.

6. Не превращать Trust в жесткий рейтинг личности.
   Trust показывается как набор подтвержденных сигналов и бейджей, а не как публичное число "хороший/плохой человек".

## Где Живет Функция

Основная точка входа: `Social -> People`.

Рядом, но не вместо:

- `Social -> Feed` - посты и события;
- `Social -> Blog` - личный блог текущего пользователя или открытый блог автора;
- `Profile` - личный профиль владельца;
- `Team` - командные связи;
- `Market` - объявления и сделки.

`People` не должен дублировать все эти разделы. Он отвечает только за поиск людей и переход к публичной странице.

`Teams` остается отдельным рабочим пространством: задачи команды, участники, лидерство, командные бонусы, коммуникация внутри своей структуры, смена лида и командные инструменты. `People` может показывать командный контекст, но не должен превращаться в панель управления командой.

## Информационная Архитектура

Рекомендуемая структура `Social`:

```text
Social
  Feed
  People
  Blog
  Profile
```

Если места мало на мобильном, `Profile` может быть в главной навигации приложения, а внутри `Social` остаются:

```text
Feed | People | Blog
```

Публичная страница пользователя открывается как отдельный экран или modal/detail view:

```text
/u/[userIdOrUsername]
/u/[userIdOrUsername]/blog
```

Для MVP можно оставить modal внутри `Social`, но дизайн должен быть готов к отдельному URL. Отдельный URL нужен для ссылок, шаринга и переходов из внешних соцсетей.

Решение по имени: `display_name` показывается в UI, но не используется как стабильный URL. Пока нет уникальных handles, route может принимать `user_id`. После появления username route остается тем же по смыслу: `userIdOrUsername`.

## Экран People

### Первый Экран

На мобильном первый экран должен показывать:

- строку поиска;
- короткие фильтры-чипы;
- список пользователей строками;
- состояние загрузки, пустой результат и ошибку;
- кнопку сброса фильтров, если активны критерии.

Не нужно делать большую hero-зону, объясняющий текст или баннер. Пользователь пришел искать людей.

### Поиск

Поиск работает по:

- имени;
- username;
- bio/короткому описанию, если оно public;
- публичным навыкам/темам;
- публичным желаниям;
- публичным постам;
- внешним ссылкам, если владелец разрешил их показывать;
- подтвержденным публичным бейджам.

Поле поиска должно быть простым, как в Telegram/Instagram:

```text
Search people, skills, goals...
```

В русской локализации:

```text
Поиск людей, навыков, целей...
```

### Быстрые Фильтры

Фильтры должны быть чипами в одну-две строки, а не большим сложным сайдбаром.

MVP-чипы:

- `Team`
- `Referrals`
- `Same Level`
- `Nearby Level`
- `Active`
- `Market`

Русские варианты:

- `Команда`
- `Рефералы`
- `Мой уровень`
- `Близкий уровень`
- `Активные`
- `Маркет`

`All` можно оставить как технический режим или поздний explore-режим, но не как бесконечную выдачу всех аккаунтов подряд. В раннем продукте default list должен быть ограничен сигналами близости: команда, рефералы, похожий уровень, активность, общие темы и публичный контент.

### Расширенные Критерии

Расширенные фильтры открываются отдельной панелью `Filters`, как в маркетплейсах и Telegram-поиске, но с легкой формой.

Критерии:

- диапазон `Level`;
- Trust-сигналы: есть подтвержденные действия, сделки, помощь, челленджи;
- Team: сила личной команды, роль leader/member, есть свободная capacity, общий лидер, общие контакты;
- Referrals: приглашенные пользователи, реферальная ветка, люди из приглашенной сети;
- Influence: активность блога, полезность постов, подписчики, реакции, комментарии, просмотры, привлеченные рефералы;
- темы: финансы, фриланс, контент, продажи, AI, обучение, здоровье, другое;
- цели/желания: похожие желания, выполненные желания, публичные цели;
- активность: сегодня, 7 дней, 30 дней;
- маркет: продает услуги/предметы, есть отзывы по объявлениям;
- язык;
- доступность: открыт для вопросов, открыт для наставничества, ищет команду.

Важно: фильтры должны работать только по данным, которые viewer имеет право видеть.

## Строка Пользователя

Строка пользователя похожа на Telegram/Instagram search result: аватар слева, текст в центре, ключевые метрики справа или под именем.

### Состав Строки

Обязательно:

- аватар;
- display name;
- username или короткий handle;
- `Level`;
- 1 строка контекста: bio, цель, роль или последняя публичная активность;
- компактные статы: `Trust`, `Team`, `Influence`;
- действие: открыть профиль по нажатию на строку.

Опционально:

- follow/unfollow;
- message/request contact;
- бейдж `Mentor`, `Creator`, `Seller`, `Team lead`;
- совпадение поиска, например `AI automation` или `public wish: build freelance income`.

### Визуальный Формат

```text
[Avatar]  Anna Petrova             L12
          AI freelancer | wants 3 stable clients
          Trust: 8 confirmed · Team: 14 · Influence: active
```

Для мобильного:

- высота строки 72-92 px;
- все тексты обрезаются аккуратно, без переполнения;
- имя в одну строку;
- контекст в одну строку;
- статы в одну строку мелкими чипами;
- не больше одного явного CTA в строке.

Для desktop:

- можно добавить правую колонку с кнопками `Follow`, `Message`, `View`;
- список остается списком, а не сеткой карточек, потому что пользователь сравнивает людей по критериям.

### Что Не Показывать В Строке

Не показывать:

- доходы и расходы, если пользователь не включил public visibility;
- точный Wallet/Core, если это не отдельный разрешенный публичный блок;
- приватные контакты;
- всю командную структуру;
- длинные описания;
- много кнопок;
- сырые технические id.

Строка должна помогать выбрать человека, а не заменять профиль.

## Публичная Страница Пользователя

Публичная страница похожа на профиль в Instagram/Telegram, но с системными статами Open Abundance.

Главная задача: за 5 секунд понять, кто человек, на каком он этапе, чем может быть полезен, что подтверждено системой, и куда перейти дальше.

### Верхний Блок

Состав:

- обложка или спокойный фон;
- аватар;
- display name;
- username;
- `Level`;
- короткий bio;
- 3-4 публичные статы;
- основные действия.

Статы:

- `Level`;
- `Trust`;
- `Team`;
- `Influence`.

Действия:

- `Follow`;
- `Message`;
- `Add contact`;
- `Ask`;
- `Blog`;
- `Share`.

Если действие недоступно, его лучше скрыть или перевести в мягкий disabled state с короткой причиной в tooltip/modal, а не показывать много объяснений на странице.

### Личка И Контакты

MVP-правило: писать можно любому пользователю. Это снижает трение в поиске людей и делает People похожим на Telegram-поиск.

Планируемое ограничение: позже у владельца профиля появятся настройки, кто может писать:

- все пользователи;
- контакты;
- команда;
- подписчики;
- никто, кроме выбранных;
- временно закрыто.

`Add contact` - это личный список viewer, не взаимная связь. Он работает как телефонная книга:

- можно добавить любого найденного пользователя;
- можно поставить пометку/тег;
- можно быстро найти человека позже;
- добавленный пользователь не получает обязательств;
- контакт не становится team member, follower или подтвержденным Trust-событием сам по себе.

Если нужен взаимный контакт или подтверждение взаимодействия, это отдельный flow через Trust/confirmation.

### Значение Стат

`Level`

Публичный системный уровень пользователя. Он всегда видим, потому что нужен для доверия, навигации и понимания масштаба прогресса.

`Trust`

Не публичный числовой рейтинг личности. Для публичной страницы лучше показывать:

- количество или диапазон подтвержденных событий, если пользователь разрешил;
- качественные бейджи: `Confirmed helper`, `Completed deals`, `Challenge proofs`;
- последние публичные подтверждения, если они public.

Текущая база Trust уже содержит `trust_events`, `mutual_confirmations`, `reciprocity_balances` и `reciprocity_score`. Для People/Profile нужен отдельный публичный summary поверх этих данных. Сырой `reciprocity_score` не должен автоматически становиться публичной оценкой человека.

`Team`

Показывает только разрешенный командный контекст:

- роль: leader/member;
- сила личной команды: сумма уровней прямых участников;
- количество прямых участников как вторичный показатель;
- свободные места, если пользователь открыт для команды;
- общие командные связи с viewer.

Если в существующей Teams-части уже хранится только количество участников, для discovery нужно добавить или вычислять team strength отдельно. Рекомендуемый MVP-лейбл: `Team strength`.

`Influence`

Показывает социальную активность без токсичного рейтинга:

- активный блог;
- подписчики/читатели, если публично;
- полезные посты;
- просмотры;
- комментарии;
- реакции/сохранения в агрегированном виде;
- привлеченные рефералы как сильный сигнал влияния;
- популярные темы автора.

В MVP точный `Influence` не считается и не блокирует разработку People. Можно показывать placeholder/status вроде `new`, `active`, `creator`, а числовой показатель оставить в плане.

### Вкладки Публичной Страницы

Чтобы не смешивать все в кучу, публичная страница должна иметь вкладки или секции:

```text
Overview | Blog | Progress | Team | Market
```

MVP:

```text
Overview | Blog
```

Следующий этап:

```text
Overview | Blog | Proofs | Team | Market
```

`Overview` показывает сжатую витрину.

`Blog` показывает посты автора.

`Proofs` показывает публичные подтверждения, достижения и Trust-события.

`Team` показывает только публично разрешенную командную часть.

`Market` показывает публичные объявления автора, если есть.

### Overview

Порядок блоков:

1. Header с человеком и статами.
2. Короткое bio.
3. Публичные цели/желания.
4. Лучшие или закрепленные посты.
5. Подтвержденные бейджи.
6. Открытые действия: follow, request contact, ask, join/request team, view market.

Каждый блок должен быть коротким. Если данных много, показывать 2-3 элемента и ссылку `View all`.

### Blog

Blog - это не отдельный чужой продукт, а публичная лента автора внутри его страницы.

Связь должна быть очевидной:

- на публичной странице есть вкладка/кнопка `Blog`;
- в блоге сверху остается compact profile header автора;
- из каждого поста можно открыть публичную страницу автора;
- кнопка `Profile` возвращает из блога в Overview;
- URL или состояние экрана сохраняет автора.

Форматы в блоге:

- ручные посты;
- daily progress posts;
- wish posts;
- external link posts;
- achievement/proof posts;
- позже media posts.

Фильтры блога:

- `All`;
- `Progress`;
- `Wishes`;
- `Proofs`;
- `Lessons`;
- `External`.

На мобильном фильтры должны быть горизонтальными чипами.

## Связь Личного И Публичного Профиля

Личный профиль владельца:

- все данные;
- настройки видимости;
- редактирование bio;
- ссылки;
- приватные и публичные блоки;
- личные подтверждения и входящие запросы;
- настройки контактов и команды.

Публичная страница:

- только разрешенные поля;
- без редактора;
- без приватных запросов;
- без внутренних Wallet/Core операций;
- без debug-информации;
- без приватных списков контактов.

Для владельца, который смотрит свою публичную страницу, можно показывать:

- переключатель `View as public`;
- кнопку `Edit visibility`;
- мягкие подсказки "этот блок скрыт от других".

Но для чужого viewer публичная страница должна быть чистой, без внутренних подсказок владельца.

## Видимость

Используются уровни:

```text
public | followers | team | contacts | private
```

Блоки видимости:

- bio;
- links;
- wishes;
- achievements;
- trust/proofs;
- team;
- posts;
- market;
- income;
- expenses.

Правила:

- avatar, display name и `Level` всегда видимы;
- username видим, если используется как публичный URL/handle;
- остальные блоки фильтруются по relation viewer -> owner;
- API публичного профиля не должен возвращать скрытые данные вообще;
- UI не должен скрывать приватное только CSS-ом.

`Level` нельзя скрыть ни в личных настройках видимости, ни в публичной выдаче People. Это базовый системный факт для навигации, доверия и ограничений возможностей.

## Навигация И Переходы

Основные переходы:

```text
People row -> Public profile Overview
Public profile -> Blog
Blog -> Public profile
Feed post author -> Public profile
Feed post -> Author blog
Team member row -> Public profile
Market listing seller -> Public profile
Public profile -> Market listings by user
Public profile -> Add contact
Public profile -> Message
```

Правило: имя и аватар пользователя в любом публичном контексте открывают его публичную страницу.

Если пользователь пришел из списка с фильтрами, кнопка назад возвращает его к тем же фильтрам и позиции скролла.

## Рекомендации По Визуальному Стилю

Брать паттерны:

- Instagram: профиль как витрина, вкладка с постами, быстрый переход от поста к автору;
- Telegram: чистый список людей, поиск сверху, строка с аватаром и коротким контекстом;
- LinkedIn: понятные роли, опыт, доверительные сигналы, но без перегруза;
- TikTok/Reels: быстрый переход от контента к автору, но без бесконечной развлекательной механики как главной цели.

Не копировать:

- агрессивные счетчики популярности;
- бесконечные рекомендации без цели;
- перегруженные профили с десятками секций подряд;
- публичные рейтинги личности;
- яркие рекламные карточки внутри профиля.

Для Open Abundance стиль должен быть спокойный, плотный, читаемый:

- строки людей вместо больших карточек в поиске;
- короткие чипы вместо длинных label;
- вкладки вместо одного бесконечного полотна;
- системные бейджи рядом с человеческим описанием;
- один главный CTA на блок.

## Пустые И Особые Состояния

People:

- нет результатов;
- фильтры слишком узкие;
- пользователь не вошел;
- нет доступа к team/followers фильтру;
- ошибка загрузки.

Публичная страница:

- профиль существует, но почти все скрыто;
- пользователь удален/недоступен;
- нет публичных постов;
- blog скрыт настройками;
- viewer заблокирован или не имеет relation для team/contact blocks.

Пустые состояния должны быть короткими и действующими:

- `No people found`;
- `Clear filters`;
- `No public posts yet`;
- `This block is private`.

## MVP Scope

В MVP входит:

- экран `People`;
- поиск по display name, username, bio и public tags/topics;
- фильтры `Team`, `Referrals`, `Same Level`, `Nearby Level`, `Active`;
- строки пользователей с avatar, name, username, level, коротким bio и public stat chips;
- публичная страница `Overview`;
- вкладка/переход `Blog`;
- связь blog <-> public profile;
- visibility-фильтрация на API;
- `View as public` для владельца;
- `Message` entry point для любого пользователя;
- `Add contact` как личный список viewer;
- переходы из feed/blog/team/market к публичной странице.

Не входит в MVP:

- сложный recommendation ranking;
- публичный numeric Trust score;
- глобальная таблица лидеров;
- детальная аналитика Influence;
- полноценный Influence score;
- продвинутые графы команд;
- публичное отображение приватных контактов;
- поиск по скрытым данным;
- настройки "кто может писать";
- autoplay media/reels.

## Data И API Набросок

Возможные endpoints:

```text
GET /api/social/people
GET /api/social/profile/[userIdOrUsername]
GET /api/social/profile/[userIdOrUsername]/blog
```

`GET /api/social/people` принимает:

```text
q
level_min
level_max
relation
active_since
topic
trust_signal
team_status
referral_status
market_status
cursor
limit
```

Ответ строки:

```text
userId
username
displayName
avatarUrl
level
headline
bioPreview
publicStats
badges
relationToViewer
lastPublicActivityAt
```

`publicStats`:

```text
level
trustSummary
teamSummary
influenceSummary
```

Важно: `trustSummary`, `teamSummary`, `influenceSummary` должны быть уже отфильтрованы по видимости.

Для скорости позже можно завести `user_discovery_index`, который хранит только публично индексируемые поля. При изменении visibility приватные поля должны удаляться из индекса.

## Ranking

Базовая сортировка MVP:

```text
exact name/username match
+ relation boost
+ recent public activity
+ nearby level match
+ shared topic/wish match
+ public trust badge match
+ blog activity
- hidden/incomplete profile penalty
```

Правила:

- новые пользователи должны иметь шанс появляться;
- команда и контакты могут получать boost, но не должны полностью вытеснять остальных;
- `All`/default выдача ограничивается ranking, лимитами и антиспам-правилами, а не возвращает всех пользователей подряд;
- market/reviews не должны превращаться в общий рейтинг личности;
- приватные данные не участвуют в public ranking.

## Anti-Spam And Safety

Первое ограничение от спама: не показывать бесконечный список всех пользователей без намерения поиска. Default People должен быть ranked discovery, где выдача ограничена:

- поисковым запросом;
- связью с viewer: team, referrals, contacts, followers;
- близким уровнем: same level или `level +/- 1`;
- активностью за последние 7/30 дней;
- общими публичными темами, желаниями или постами;
- лимитом выдачи и cursor pagination.

Для сообщений:

- rate limit на первые сообщения незнакомым людям;
- кнопка block/report позже;
- настройки "кто может писать" позже;
- новые/низкоактивные аккаунты получают более строгий лимит исходящих сообщений;
- массовое одинаковое сообщение нескольким людям должно считаться подозрительным.

Для контактов:

- добавление в личные контакты не уведомляет второго пользователя;
- контакт не дает доступ к скрытым данным автоматически;
- доступ к `contacts`-visible данным должен требовать отдельного подтвержденного отношения, если продукт решит сделать contacts взаимной приватной группой.

## Acceptance Criteria

- Пользователь может открыть `Social -> People` и увидеть список людей строками.
- Пользователь может искать по имени, username и публичному описанию.
- Пользователь может фильтровать хотя бы по команде, рефералам, активности и близкому уровню.
- Нажатие на строку открывает публичную страницу пользователя.
- Публичная страница показывает `Level`, `Trust`, `Team`, `Influence` только в разрешенном виде.
- `Level` виден всегда и не скрывается настройками.
- Из публичной страницы можно открыть блог автора.
- Из блога можно вернуться на публичную страницу автора.
- Пользователь может написать другому пользователю из публичной страницы.
- Пользователь может добавить другого пользователя в личные контакты без взаимного подтверждения.
- Avatar/name автора в feed, blog, team и market ведут на одну и ту же публичную страницу.
- Скрытые владельцем блоки не возвращаются публичным API.
- Личный профиль и публичная страница имеют разные режимы: owner редактирует и настраивает, viewer смотрит чистую публичную версию.
