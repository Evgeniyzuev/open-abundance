# Open Abundance Master Kanban

Этот документ — единственный канонический источник оперативного статуса Open Abundance. Конкретные решения живут в `OPEN_ABUNDANCE_MASTER_PLAN.md`, накопительный контекст — в `PROJECT_MEMORY.md`; тематические планы не меняют порядок работы в этом канбане.

## Правила работы

- Одновременно в `Сейчас` находится ровно одна главная продуктовая карточка.
- Путь карточки: `Очередь -> Сейчас -> Technical QA -> User QA -> Подтверждено`.
- Написанный код не равен готовому продукту. Без ручной проверки сценария карточка остается в `Технически реализовано / нужен User QA`.
- Перед реализацией следующей карточки фиксируется короткий decision-complete план.
- Код, связанный продуктовый документ и этот канбан обновляются в одной итерации.
- Новые идеи идут в очередь и не прерывают текущий шаг, кроме критических ошибок и угрозы деньгам или данным.
- После frontend-изменений выполняется одна попытка визуальной проверки в in-app browser. Если он недоступен, это явно фиксируется вместе с результатами технических проверок.

## Формат активной карточки

Активная карточка содержит:

- пользовательский результат;
- причину приоритета;
- конкретные изменения;
- что не входит в шаг;
- критерии приемки;
- технические проверки;
- ручной UX-сценарий;
- продуктовую метрику;
- найденные блокеры;
- ссылку на подробный план, если он нужен.

## Сейчас

### MVP receipt после награды Core

- **Статус:** Сейчас — reward начисление в Core проверено пользователем; упрощенный UI receipt реализован, нужен ручной UX QA.
- **Пользовательский результат:** после подтвержденного challenge пользователь сразу видит короткую квитанцию: какой challenge завершен, каким способом проверен, сколько Core начислено и какой Core-баланс получился после операции.
- **Почему сейчас:** Home/Today уже доводит пользователя до действия, а receipt замыкает понятный цикл `действие → проверка → Core → следующий шаг` без преждевременного финансового интерфейса.
- **Главное решение:** для MVP используем существующий server completion response и его фактически проверенное начисление в `Core`; receipt остается UX-подтверждением, а не финансовой выпиской. Ledger ID, полноценная история, before/after contract и Wallet payout переносятся в финансовый этап.
- **Изменения:**
  - сохранить серверную проверку и начисление без изменения финансовой схемы;
  - передать в completion modal название challenge, тип verification, сумму reward и Core после начисления;
  - показать компактный receipt в Challenges и сохранить существующий refresh Challenges/Today/Home;
  - позже, вместе с финансовой частью, добавить ledger event/id, timestamp, полноценную историю и пересчет server-side личного плана.
- **Не входит:** ledger migration/RPC redesign, финансовая выписка, Wallet-ввод/вывод, внешние выплаты, team/referral rewards, before/after Wallet contract, изменение server-side GrowthPlan и публичный feed.
- **Критерии приемки:** успешный Core challenge показывает receipt с challenge/verification/reward/Core after; сумма и баланс берутся из ответа сервера; повторный check не создает повторного начисления; после закрытия receipt пользователь видит актуальные Challenges/Today/Home.
- **Технические проверки:** `pnpm exec tsc --noEmit`, `pnpm lint`, ручной UX-сценарий `challenge → check → receipt → Home/Today`; e2e полного reward loop остается отдельной проверкой при доступном runtime-каталоге.
- **Ручной UX-сценарий:** принять первый доступный Core challenge, выполнить проверяемое действие, нажать check, убедиться в receipt и новом Core-балансе, закрыть его и проверить Today/Home; повторный check не должен увеличивать награду.
- **Метрика:** доля завершенных Core challenges с видимым receipt и доля пользователей, которые после receipt переходят к следующему Today/Home действию.
- **Блокеры:** для MVP нет; полноценный ledger proof и финансовая история сознательно отложены до финансового этапа.
- **Связанные документы:** `docs/PROJECT_MEMORY.md`, `docs/TODAY_DAILY_CHALLENGE_PLAN.md`, `docs/CHALLENGES_CATALOG.md`.

## Критерии закрытого пилота

- Когорта: 20-50 лично приглашенных русскоязычных пользователей.
- Не менее 70% создают главное желание и сохраняют финансовый план.
- Не менее 50% получают первый проверяемый результат или понимают срок и способ его проверки.
- Ориентиры удержания: D1 >= 40%, D3 >= 25%, D7 >= 15%.
- Не менее 30% активированных участников публикуют карточку результата.
- Не менее 20% активированных участников отправляют приглашение.
- Каждое Wallet-начисление имеет источник, ledger-запись, защиту от повторного начисления и покрытие фондом.
- Демо-контент всегда визуально и семантически отделен от реальных результатов.
