# Продажа подписок и приложений через ОА (APPS-001)

Версия 1 · 2026-10-22. План по запросу основателя.

## 0. Решения основателя

- Для продуктов пользователей ОА только площадка (маркетплейс). Продавец продаёт от своего имени и сам отвечает за продукт, ОА даёт витрину, оплату из Wallet, escrow, подбор покупателей и проверку объявлений.
- Долю цены, которая идёт в Core покупателя (coreShare), продавец задаёт сам при выставлении товара. В документах конкретные доли не фиксируем.
- На пилоте без обязательных юридических договоров: продавец принимает правила площадки при создании объявления.
- Детали (сроки, лимиты, размеры) делаем настраиваемыми параметрами и подбираем после запуска, сначала нужен работающий механизм.

## 1. Коротко

Продавец приложения, бота или онлайн-сервиса выставляет в маркетплейсе объявление вида «цифровой доступ» или «подписка». Покупатель платит из Wallet. Доступ выдаётся автоматически одним из трёх способов: ключ из загруженного продавцом пула, подписанный webhook на сервер продавца или ручная выдача через существующий поток сделки. Подписка продлевается списанием из Wallet раз в период с согласия покупателя и отменяется в один клик. ОА показывает предложение людям, у которых есть похожее желание или запись «присматриваюсь купить».

Ценность для продавца: живые заинтересованные люди, отзывы и тестеры, оплата без комиссии внутри ОА, возможность сделать покупателя соучастником через Core.

## 2. Что уже есть и что переиспользуем

| Есть в коде | Как используем |
|---|---|
| `marketplace_listings` с `listing_kind` (`digital_asset`, `service`, `physical_good`), `metadata` Json | добавляем виды `digital_access` и `subscription` |
| `marketplace_deals` + `marketplace_escrows`, идемпотентные hold/release/refund RPC | каждая покупка и каждый период подписки это отдельная сделка |
| Wallet (`wallet_ledger`, `wallet_transfer`), переводы без комиссии | оплата и выплата продавцу |
| Доля в Core при покупке (`shopCoreBonus`, `buy_system_item`) | тот же приём для coreShare продавца |
| `lib/marketplaceListingCheck.ts`, очередь оператора | проверка новых объявлений и ссылок продавца |
| Публичные страницы `/m/[listingId]`, мастерская `/@nick/shop` | витрина и ссылка на оплату |
| `wish_products`, spend-intents, тексты желаний | сигналы для подбора покупателей |
| Отзывы маркетплейса, трек `business` | доверие и челленджи для продавцов |

## 3. Шаги

### Шаг 1. Новый вид объявления «цифровой доступ»

1. Миграция: расширить `marketplace_listings_listing_kind_check` значениями `digital_access` и `subscription`; колонки `delivery_mode text` (`key_pool`, `webhook`, `manual`), `billing_period_days int null` (null у разовой покупки), `core_share numeric` (0..1, задаёт продавец).
2. Форма создания объявления: тип продукта (приложение, бот, сервис, курс), платформы (web, Android, iOS, Telegram), ссылка на продукт, цена, период, способ выдачи, доля в Core.
3. Правила площадки показываются один раз при первом таком объявлении: продавец отвечает за продукт и возвраты в рамках правил ОА, запрещены обещания дохода, сбор паролей и платёжных данных.
4. Проверка `marketplaceListingCheck` дополняется: ссылка продавца проверяется на доступность и на совпадение домена с заявленным продуктом.

Результат: объявление выставлено, видно в маркетплейсе, но купить его пока можно только с ручной выдачей.

### Шаг 2. Выдача доступа ключами

1. Таблица `listing_access_keys` (listing_id, ключ в зашифрованном виде, status `free/issued/revoked`, deal_id, issued_at). Продавец загружает ключи пачкой (CSV или по строке), видит остаток.
2. При завершении оплаты RPC в той же транзакции берёт свободный ключ (`for update skip locked`) и привязывает его к сделке. Нет свободных ключей: объявление автоматически скрывается, продавцу уведомление.
3. Покупатель видит ключ и инструкцию продавца в «Покупках» и в карточке сделки.
4. Escrow: деньги держатся параметрический срок (по умолчанию 3 дня) на случай «ключ не работает», затем уходят продавцу. Спор идёт по существующему потоку dispute.

Результат: продавец без единой строки кода продаёт лицензии, промокоды и инвайты.

### Шаг 3. Ссылка на оплату и кнопка

1. Страница `/pay/[listingId]`: цена, что получает покупатель, доля в Core, вход или регистрация, оплата из Wallet, пополнение Wallet, если не хватает.
2. Параметры ссылки: `ref` (идентификатор покупателя у продавца, до 64 символов), `return_url` (только домен из объявления).
3. Кнопка-виджет для сайта продавца: небольшой `<a>` с иконкой и ценой, без скриптов. Для Telegram-бота продавца та же ссылка в inline-кнопке.
4. Ссылка ведёт и новых людей: регистрация через `/pay/...` засчитывается как приход с источником `utm_source=seller`, реферальная связь не создаётся (продавец не получает реферальных наград за покупателей).

Результат: продавец ставит «Оплатить через Open Abundance» у себя и получает покупателей из своей аудитории.

### Шаг 4. Webhook и проверка доступа

1. В настройках мастерской продавец получает секрет и указывает URL webhook.
2. События: `access.granted`, `access.renewed`, `access.cancelled`, `access.refunded`. Тело: id события, listing_id, buyer_ref (псевдоним покупателя для этого продавца, не user id ОА), `ref` из ссылки, `paid_until`, сумма. Подпись HMAC-SHA256 заголовком, повторы с нарастающей паузой до 24 часов, журнал доставок у продавца.
3. Эндпоинт `GET /api/seller/v1/access?buyer_ref=...` с ключом продавца: активен ли доступ и до какой даты. Нужен продавцам, которые не хотят хранить состояние.
4. «Войти через ОА» (OAuth с согласием, только псевдоним и статус доступа) откладываем: ссылка с `ref` закрывает большинство случаев.
5. Пример интеграции на 30 строк (Node.js и Python) на английской странице `/en/guide/...` для разработчиков.

Результат: доступ включается и выключается в продукте продавца автоматически.

### Шаг 5. Подписка с продлением из Wallet

1. Таблица `marketplace_subscriptions` (buyer, listing, price и period на момент оформления, status `active/past_due/cancelled`, current_period_end, auto_renew).
2. Продление: плановая задача раз в час находит подписки с истекающим периодом, создаёт новую сделку с идемпотентным ключом `sub:<id>:<period>`, списывает из Wallet. Не хватило денег: статус `past_due`, льготный срок (параметр, по умолчанию 3 дня), напоминание, затем `cancelled` и событие `access.cancelled`.
3. Отмена в один клик в «Покупках», доступ сохраняется до конца оплаченного периода. Изменение цены продавцом действует только на новые подписки или после явного согласия покупателя.
4. За напоминание о продлении отвечает существующая система уведомлений, за день до списания.
5. Escrow для подписки: деньги за период уходят продавцу после короткого срока (параметр), возврат за текущий период по правилам площадки.

Результат: подписки работают без App Store и Play Market внутри ОА.

### Шаг 6. Подбор покупателей по желаниям

1. Продавец при выставлении описывает, какое желание закрывает продукт, в одной фразе. ИИ на существующем шлюзе (Gemini, Groq, Cerebras) сопоставляет её с желаниями, `wish_products` и spend-intents, без отправки личных данных продавцу.
2. Покупатель видит предложение в карточке своего желания с пометкой «может помочь с этим желанием» и в блоке маркетплейса «Под твои желания». Не чаще параметра (например, одно предложение в день), с кнопкой «не показывать такое».
3. Продавец видит только агрегаты: «столько-то человек с похожим желанием», минимум 5 человек, как в карте спроса.
4. Без платного продвижения: порядок зависит от совпадения, рейтинга отзывов и доли возвратов, не от денег.

Результат: заинтересованные люди находят продукт сами, продавец видит размер спроса.

### Шаг 7. Доверие и челленджи для продавцов

1. Челленджи трека `business` для продавцов приложений: первое объявление с цифровым доступом, первый покупатель, первые 3 отзыва, первый продлённый период подписки, интеграция webhook. Награда как у других шагов трека (Core +1 $).
2. Первые покупатели проверяют продукт: продавец может включить «цену для первых» и обязательный отзыв, как у продуктов ОА.
3. Быстрое скрытие при жалобах и доля возвратов в карточке продавца.

### Шаг 8. Поиск первых продавцов

1. Изнутри: участники трека `business`, у кого есть приложение или бот.
2. Создатели Telegram-ботов с ИИ на подписке.
3. Русскоязычные инди-разработчики: vc.ru, Хабр, чаты разработчиков Mini Apps и TON. Для России сильный довод: выплаты из App Store фактически недоступны.
4. Международные: Indie Hackers, r/SideProject, X #buildinpublic, авторы Product Hunt.
5. Цель первой волны: 10 продавцов, у каждого хотя бы один покупатель из ОА.

## 4. Правила магазинов и Telegram

ОА не может обойти правила магазинов внутри чужих приложений, поэтому продавцу показываем короткую памятку при выборе платформ:

- **Веб и сайт продавца:** ограничений нет.
- **Telegram-бот (обычные платежи в чате) и ссылка из бота:** допустимо.
- **Внутри Telegram Mini App:** цифровые товары по правилам Telegram продаются за Stars. Оплату через ОА ведём ссылкой в веб, а не внутри Mini App. Это касается и собственного Mini App ОА: покупка цифрового доступа в нём открывает веб-страницу оплаты.
- **Android вне Google Play (APK, RuStore и другие):** ограничений Google нет, действуют правила своего магазина.
- **Google Play:** в США ссылки на внешнюю оплату разрешены после дела Epic; в других странах действуют программы альтернативной оплаты с комиссией.
- **iOS:** ссылка на внешнюю оплату разрешена в США (с 2025 года) и в ЕС по DMA с платой Apple. В остальных странах встроенная ссылка на внешнюю оплату внутри iOS-приложения нарушает правила; продавец может продавать подписку на сайте, а приложение только проверяет доступ (модель «reader app» и «аккаунт создан вне приложения»).

Состояние правил записано по данным середины 2026 года; перед запуском шага 3 и перед первой рассылкой продавцам сверить актуальные правила Apple, Google и Telegram.

## 5. Риски и как их закрываем

| Риск | Мера |
|---|---|
| ОА выглядит платёжным посредником | продавец продаёт от своего имени, оплата только внутренним Wallet между участниками, без приёма карт на пилоте (см. [ACQUIRING_COMPARISON.md](ACQUIRING_COMPARISON.md)) |
| Мошенничество, пустые ключи, исчезнувший сервис | escrow на срок проверки, споры, скрытие при жалобах, доля возвратов в карточке, лимит новых аккаунтов из `marketplaceListingCheck` |
| Обещания дохода в описаниях | существующий фильтр формулировок, отдельное правило для подписок «заработок» |
| Утечка личных данных покупателей | продавец получает только buyer_ref и `ref` из своей ссылки |
| Вывод денег продавцом только в крипте | честно писать в памятке; P2P Wallet ↔ RUB как второй путь |
| Маленькая аудитория на старте | ссылка на оплату приводит аудиторию продавца в ОА, это рост для обеих сторон |

## 6. MVP и порядок

1. Шаги 1–3 (вид объявления, ключи, ссылка на оплату): первый работающий результат без кода у продавца.
2. Шаг 5 (подписки) вместе с шагом 4 (webhook): автоматизация для разработчиков.
3. Шаги 6–7 (подбор и челленджи) после первых 10 продавцов.

Метрики: число продавцов с цифровым доступом, покупок и продлений в неделю, доля споров и возвратов, доля новых пользователей, пришедших по ссылкам продавцов.
