# Ежедневная аналитика

Один скрипт собирает из базы одну сводку в Markdown и файлы с деталями. Claude читает сводку, выбирает 1–3 решения на день и готовит действия. Всё, что касается людей напрямую (рассылки, выплаты, опросы с наградой), идёт только после подтверждения Evgen.

Код: `lib/dailyAnalytics.ts` (сбор и сводка), `scripts/daily-analytics.mjs` (запуск), `app/api/internal/analytics/daily/route.ts` (запуск без ключа базы), тест `pnpm test:daily-analytics`. Миграций не нужно.

## 1. Что собираем

| Раздел сводки | Откуда | Что видно |
| --- | --- | --- |
| Пульс | `user_profiles`, `product_events` | аккаунты, новые, активные за 1/7/30 дней (с гостями и без), залипание |
| Воронка | `product_events` (onboarding_*), воронка координатора | онбординг гостей, путь участника по 12 шагам, самое узкое место |
| Движения людей | `product_events` | топ-25 событий за сутки и 7 дней, активные часы |
| Желания | `wishes`, `recommended_wishes` | новые, выполненные, суммы, категории, что берут из рекомендованных |
| Навыки и совпадения | `skills`, `user_skills`, `user_help_profiles` | навыки и подтверждения, теги «нужно / могу», спрос без предложения, возможные пары по согласию |
| Лента и связи | `feed_posts`, `feed_post_comments`, `feed_post_likes`, `direct_messages`, `user_follows` | посты, комментарии, лайки, личные сообщения (только счёт, без текста), подписки |
| Челленджи и проверка | `challenges`, `user_challenges`, `peer_review_answers`, `challenge_feedback_submissions`, события `*check_failed*` | взято/выполнено, застрявшие 3+ дня, очередь взаимной проверки, неудачные автопроверки, оценки |
| Рефералы | `referral_edges`, `humanity_verifications` | приглашённые, доля прошедших проверку, источники |
| Core и Wallet | `core_accounts`, `wallet_accounts`, `user_economy_metrics`, `wallet_ledger` | Core всего/медиана/p90, Джини, состав нового Core, вердикт справедливости, операции Wallet |
| Маркетплейс и расходы | `marketplace_listings`, `marketplace_deals`, `user_spend_intents` | объявления, проверка перед показом гостям, сделки, категории расходов |
| Голос людей | `user_feedback`, ответы «помогло ли», `ai_usage_events`, `push_subscriptions`, `telegram_accounts` | жалобы по экранам, удовлетворённость, Нова, сбои ИИ, сколько людей достижимо пушем |
| Персональные шаги | всё выше | сколько людей на каком следующем шаге (лестница ниже) |
| Что предлагать | сигналы выше | шесть направлений: доход, рост, обучение, развлечения, желания, решение проблем |
| Предложения действий | правила координатора | что сделать и для скольких людей, только после подтверждения |

Детали лежат рядом со сводкой в `details/*.json`: события, публичные желания, комментарии к публичным постам, челленджи, объявления, отзывы, персональные шаги, предложения. Сравнение со вчера скрипт добавляет сам, если в папке есть вчерашний `metrics.json`.

**Правила приватности.** В сводке только числа. В деталях люди названы псевдонимом `u_xxxxxxxxxx` (HMAC от id; секрет `ANALYTICS_PSEUDONYM_SALT` или производный от ключа сервиса), имён, ников и почты нет. Личные признаки (нужды, предложения, категории расходов) показываются группами от 5 человек, мелкие группы сливаются в «другое». Текст выходит только тот, что человек писал для других: публичные желания, комментарии к публичным постам, объявления, отзывы команде. Личные сообщения, приватные желания, заметки и рефлексии не читаются. Отчёты пишутся в `reports/`, папка в `.gitignore`.

## 2. Как превращать в решения

Каждый день Claude делает одно и то же:

1. Смотрит «Изменения со вчера» и узкое место воронки.
2. Берёт раздел «Что предлагать» и выбирает не больше трёх решений. Каждое решение опирается на конкретную строку сводки.
3. Для каждого решения пишет: что меняем, для кого (размер группы), какую метрику ждём сдвинуть и когда проверим.
4. Через день-три проверяет эту метрику в той же сводке и записывает результат в очередь рекомендаций (`coordinator_recommendations.outcome`), чтобы правила учились на итогах.

Направления и сигналы (стартовые правила в `productSignals`, дальше их настраивает ИИ):

| Направление | Сигнал | Типичное решение |
| --- | --- | --- |
| Доход | объявления без продаж, готовность перенести расходы, нужда `first_client` | челлендж «первая продажа», продукт OA в частой категории расходов |
| Рост | застрявшие в задании, нет задания при желании, низкий возврат на 2-й день | дробить первый шаг до 5 минут, цепочки из 3 шагов с наградой за каждый |
| Обучение | спрос без предложения по тегам, навыки без подтверждения | мини-курс + челлендж, поиск наставника, подтверждение навыка |
| Развлечения | комбо дня, просмотры ленты без действий | сюрприз в саду за серию, загадки от участников |
| Желания | частые категории, выбор из рекомендованных | готовый путь к желанию с шагами и продуктом внутри OA |
| Решение проблем | жалобы по экранам, неудачные автопроверки, сбои ИИ | починить экран из топа жалоб, переписать непонятную проверку |

## 3. Как и когда запускать

**Частота:** раз в день утром (06:00 UTC = 09:00 МСК), плюс раз в неделю разбор недели по тем же файлам.

Три способа, от простого к удобному:

| Способ | Команда | Что нужно |
| --- | --- | --- |
| Пробный, без данных | `pnpm analytics:daily --fixtures` | ничего |
| На компьютере Evgen | `pnpm analytics:daily` | `.env` с `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` (уже есть) |
| С телефона / в облачной сессии Claude | `pnpm analytics:daily --source=api` | только `ANALYTICS_READ_TOKEN`, ключ базы не нужен |

**Нужен ли ключ базы для запуска с телефона? Нет.** Ключ сервиса остаётся только в Vercel. Маршрут `/api/internal/analytics/daily` строит отчёт на сервере и отдаёт его по отдельному токену `ANALYTICS_READ_TOKEN`. Этот токен умеет только читать готовую сводку с псевдонимами: им нельзя писать в базу, читать таблицы или узнать id людей. Если он утечёт, худшее — кто-то увидит агрегаты; токен меняется за минуту в Vercel. Порог групп через API можно только поднять, не опустить.

Что сделать один раз:

1. Сгенерировать токен: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
2. Vercel → Settings → Environment Variables: `ANALYTICS_READ_TOKEN` = токен (Production), передеплой.
3. В облачном окружении Claude (настройки проекта → Cloud environment → шестерёнка): добавить секрет `ANALYTICS_READ_TOKEN` и разрешить домен `open-abundance.vercel.app` в Network access (сейчас он закрыт).
4. После этого с телефона достаточно написать в проекте «запусти аналитику», или поставить ежедневную routine на 06:00 UTC.

Почему не GitHub Actions: отчёт с псевдонимами и текстами отзывов попадёт в логи и артефакты CI, а их проще случайно открыть. Облачная сессия Claude или компьютер Evgen надёжнее.

Альтернатива на будущее, если понадобится прямой доступ к таблицам без ключа сервиса: отдельная роль Postgres только с `SELECT` на нужные столбцы или RPC-функции `security definer`, которые возвращают только агрегаты. Сейчас это не нужно: маршрут с токеном закрывает задачу без миграций.

## 4. Действия по итогам

Скрипт ничего не отправляет. Действия идут через то, что уже есть в приложении:

- **Очередь рекомендаций** (`coordinator_recommendations`, панель оператора): сюда попадают предложения правил и решения Claude, Evgen одобряет или отклоняет.
- **Подсказки следующего шага** (`/api/internal/coordinator/nudges`): уже умеют слать один пуш «следующий шаг» застрявшим, включаются флагом `COORDINATOR_NUDGES_ENABLED=1`.

- **Входящие от Новы** (`POST /api/internal/nova/inbox`, миграция `20261023120000_nova_inbox.sql`): личное сообщение одному человеку. Оно появляется в его чате Новы как сообщение Новы с пометкой «Нова написала вам», а пуш открывает этот чат. Человек отвечает прямо в чате. Получатели указываются псевдонимами из сводки (`u_…`), имён Claude не видит. Ограничения: до 20 человек за вызов и не чаще одного сообщения в 3 дня на человека. С `"dryRun": true` вызов только показывает, кому уйдёт сообщение. Вызывать могут оператор (войдя в приложение) или Claude с токеном `CLAUDE_ACTIONS_TOKEN` (секрет в Vercel и в окружении Claude; тот же токен для оценки ответов ИИ), всегда после одобрения Evgen. **Хранение:** переписка с Новой живёт только на устройстве, поэтому сервер держит сообщение до доставки. Чат сначала сохраняет его на устройстве, потом отмечает «доставлено», а ночная задача `cleanup_nova_inbox` удаляет доставленные через сутки и недоставленные через 14 дней.

**Лестница персональных шагов** (`nextStepFor`), по одному шагу на человека:

| Шаг | Когда | Что предложить |
| --- | --- | --- |
| return_gently | не заходил 7+ дней | одно тёплое сообщение о его желании или новом в приложении |
| add_first_wish | нет желания | помочь записать одно желание |
| smaller_step | взял задание и 3+ дня без движения | шаг поменьше |
| first_challenge | есть желание, нет задания | один маленький челлендж |
| match_helper | согласен на знакомства и есть нужда | пара по тегам |
| invite_friend | есть результат, никого не приглашал | пригласить одного человека |
| ask_survey | активен, ни разу не отвечал на вопросы | короткий опрос |
| keep_going | всё идёт | не трогать, только поздравить по факту |

**Как обращаться к людям, не показывая слежку и честно.** Сообщение говорит только о том, что человек сам знает о себе в приложении: его желание, его задание, его навык. Не упоминаем, когда и сколько он заходил, что смотрел, как долго молчал. Не больше одного сообщения в неделю на человека, всегда с кнопкой «не сейчас». В политике конфиденциальности уже есть «продуктовые события для понимания работы функций»; стоит добавить одну фразу: «мы используем активность в приложении, чтобы предлагать подходящие задания и подсказки; отключить можно в настройках уведомлений».

**Опросы с наградой.** Механика: «Вопрос дня» как челлендж с `wallet_reward_amount = 0.1`, один-три вопроса с выбором, награда за ответ, не за «правильный» ответ. Начисление в Wallet даёт повод для уведомления о награде; если пуш о награде не приходит, приглашение к опросу отправляется отдельным пушем через центр уведомлений. Бюджет: 0,1 × число ответивших в день, видно в сводке в операциях Wallet. Вопросы выбирает Claude по пробелам в данных (например, «что мешает начать первое задание?» для застрявших). Запуск каждого опроса и любые выплаты — после подтверждения Evgen.

**Персональные задания.** Из лестницы выше: Claude готовит текст задания под шаг, группу и ожидаемую метрику, кладёт в очередь рекомендаций. После одобрения задание появляется у человека как обычный челлендж или подсказка.

## 5. Полный цикл: данные → изменения → применение

1. **Данные.** Сессия Claude запускает `pnpm analytics:daily --source=api` и читает сводку.
2. **Изменения.** Claude готовит код и, если нужно, миграцию в `supabase/migrations/`, проверяет tsc, lint, build и тесты.
3. **Пуш.** Claude пушит в main. Vercel сам выкатывает код.
4. **Применение.** Если в пуше есть миграции, запускается `.github/workflows/supabase-migrations.yml`. Задача `plan` показывает список файлов и начало их SQL, задача `apply` ждёт, пока Evgen нажмёт **Approve** (GitHub присылает уведомление; на телефоне: приложение GitHub → Actions → запуск → Review deployments). После этого `supabase db push` применяет миграции, при сетевом сбое пробует ещё 3 раза, а в конце пишет историю миграций в сводку запуска.
5. **Проверка.** На следующий день сводка показывает, сдвинулась ли метрика.

Код должен работать и до применения миграции (новые таблицы и столбцы читаются как «нет данных»), потому что Vercel выкатывает код раньше, чем Evgen одобрит миграцию.

**Почему раньше GitHub Actions «нестабильно» работали с Supabase.** Прямой адрес базы `db.<ref>.supabase.co` доступен только по IPv6, а у раннеров GitHub IPv6 нет. Поэтому workflow ходит через **session pooler** (IPv4, порт 5432), который не требует IPv6. Временные сбои сети workflow переждёт и повторит попытку. Ошибку в самой миграции он повторять не станет: сразу остановится и покажет её.

Что настроить один раз (GitHub → репозиторий → Settings):

1. Environments → New environment → `production`. Включить **Required reviewers** и выбрать `Evgeniyzuev`. Deployment branches: только `main`.
2. В этом окружении (не в общих секретах репозитория) добавить секрет `SUPABASE_DB_URL`: Supabase → Project → Connect → Session pooler → строка подключения с паролем базы. Тогда секрет видит только задача, которую вы одобрили.
3. Ручной запуск, например для миграций, которые накопились раньше: Actions → Supabase migrations → Run workflow.

Если миграция с более ранней датой не применена, а более поздние уже в базе, `db push` откажется её применять. Такой случай Claude разбирает отдельно и не обходит его флагом `--include-all` без вашего согласия.

### Вариант без GitHub: Claude применяет миграции сам из облачной сессии

Прямое подключение к Postgres из облачной сессии не проходит, сеть там пускает только HTTPS. Поэтому `pnpm db:apply` (`scripts/apply-migrations-api.mjs`) применяет миграции через Supabase Management API. Учёт тот же, что у `supabase db push`: таблица `supabase_migrations.schema_migrations`. Без флага скрипт только показывает список, с `--apply` применяет по одной, каждую в своей транзакции, и останавливается на первой ошибке. Миграцию старше последней применённой он без `--include-all` не трогает.

Настройка (один раз):

1. Supabase → аватар → Account preferences → **Access Tokens** → Generate new token, назвать например `claude-migrations`. Токен даёт полный доступ к вашим проектам Supabase, поэтому храните его только в секретах окружения и отзовите, если окружение больше не нужно.
2. Claude, настройки проекта → Среда:
   - **Сетевые секреты** (Добавить): хост `api.supabase.com` — токен из шага 1; хост `open-abundance.vercel.app` — `CLAUDE_ACTIONS_TOKEN`. Прокси сам подставляет токен в запросы к этому хосту, Claude его не видит, поэтому скрипты работают без токена в переменных. Один токен на хост: `CLAUDE_ACTIONS_TOKEN` открывает и сводку аналитики, и действия.
   - **Network access**: «Облачная среда» → шестерёнка у выбранной среды (Default) → уровень Limited, в Allowed domains добавить `api.supabase.com` и `open-abundance.vercel.app`, галочку «Allow package managers» оставить.
   - В Vercel → Settings → Environment Variables добавить `CLAUDE_ACTIONS_TOKEN` (и при желании `ANALYTICS_READ_TOKEN` для чтения с других устройств), затем Redeploy.
3. Начать новую сессию: окружение подхватывается при старте.

Порядок работы: Claude показывает `pnpm db:apply` (список) и SQL в треде, вы пишете «применяй», Claude запускает `pnpm db:apply --apply` и проверяет таблицы. Это быстрее workflow, но подтверждение здесь — ваше сообщение в треде, а не кнопка GitHub.

## 6. Порядок на каждый день

1. `pnpm analytics:daily` (или `--source=api`).
2. Claude читает `reports/analytics/<дата>/summary.md`, при необходимости `details/*.json`.
3. Claude пишет в проект: 1–3 решения с опорой на цифры, что нужно подтвердить.
4. После «да» от Evgen — запуск через очередь рекомендаций или подсказки; через 1–3 дня — проверка по сводке.
