# Таксономия активностей и правил наград

Статус: план, не реализация.

Этот документ фиксирует модель разделения текущих челленджей на `challenge`, `mission`, `quest` и `task`, а также отделяет тип активности от правил распределения награды.

## 1. Основная идея

Не следует использовать четыре слова как взаимозаменяемые синонимы. Нужны две независимые оси:

1. `activity_type` — что представляет собой активность;
2. `reward_mode` — как распределяется её награда.

Публичный каталог остаётся единым. Таблица `public.challenges` и существующие API сохраняются ради совместимости, даже если в ней будут храниться разные типы активностей.

## 2. Типы активностей

| Тип | Назначение | Типичная награда |
| --- | --- | --- |
| `challenge` | Открытый конкурс с ограниченным числом победителей или мест | Первые `N` или лучшие `N` |
| `mission` | Самостоятельное персональное задание с проверяемым результатом | Гарантирована каждому, кто выполнил условия |
| `quest` | Контейнер из последовательных mission-шагов с общим прогрессом | Финальная награда за завершение цепочки |
| `task` | Одно конкретное действие внутри mission/quest либо обычная личная/командная задача | Обычно без отдельной денежной награды |

`task` не становится отдельной карточкой в каталоге Challenges в первой версии. Личные локальные tasks, Today tasks и командные `team_tasks` остаются своими сущностями и не превращаются автоматически в денежные challenges.

### 2.1 Challenge

`challenge` используется, когда участники соревнуются за ограниченную награду. В карточке должны быть явно видны:

- число доступных мест или лимит победителей;
- срок завершения, если он есть;
- критерий победы — порядок подтверждения или score;
- предупреждение, что выполнение условий не всегда означает получение награды.

### 2.2 Mission

`mission` — персональное системное задание. После подтверждения результата награда гарантируется, если пользователь выполнил все условия и не нарушил правила проверки.

Mission может быть доступна всем пользователям или открываться по уровню, prerequisite, track или другому существующему правилу eligibility.

### 2.3 Quest

`quest` — родительская активность, объединяющая последовательность mission-шагов. В первой версии:

- quest имеет общий прогресс;
- шаги имеют порядок и могут зависеть друг от друга;
- финальная награда принадлежит quest;
- дочерние шаги не выплачивают отдельную денежную награду, чтобы один результат не оплачивался дважды.

Существующие `track_key`, `track_step` и `prerequisite_challenge_id` сохраняются для обратной совместимости. Для новых quest-последовательностей предпочтительно иметь явную связь с quest и порядок шага.

### 2.4 Task

Task — минимальная единица действия: написать текст, пройти проверку, отправить результат, выполнить шаг или помочь другому участнику.

Task может быть:

- шагом mission или quest;
- локальной личной задачей;
- заданием в Teams.

Task не должен автоматически получать reward accounting, если для него не создана отдельная системная mission с серверной проверкой и правилами награды.

## 3. Правила распределения награды

`reward_mode` хранится отдельно от `activity_type`.

### `guaranteed`

Каждый пользователь, который валидно завершил активность, получает указанную награду.

Это режим для текущего большинства системных mission и для совместимых legacy-записей.

### `first_n`

Награду получают первые `N` пользователей, чьё выполнение было подтверждено сервером.

Время клика, принятия активности или отправки клиентского запроса не является основанием для победы. При одновременных запросах место выдаётся атомарной серверной транзакцией.

### `top_n`

Награду получают лучшие `N` участников по серверному score после закрытия конкурса.

До окончания конкурса валидное выполнение получает статус `pending`, но не выплачивается. После дедлайна участники сортируются:

1. по убыванию score;
2. при равенстве — по более раннему серверному подтверждению completion.

Лимит `N` остаётся строгим.

Общий prize pool, распределение пропорционально score и ручной выбор победителей в MVP не входят.

## 4. План изменений модели данных

### 4.1 `public.challenges`

Добавить поля:

- `activity_type` с допустимыми значениями `challenge`, `mission`, `quest`;
- `reward_mode` с допустимыми значениями `guaranteed`, `first_n`, `top_n`;
- `reward_limit` — лимит победителей для конкурсных режимов;
- `competition_closes_at` — дедлайн конкурса;
- `ranking_metric` — серверное правило или идентификатор score для `top_n`;
- `quest_id` — ссылка на родительский quest для дочерней активности;
- `step_order` — порядок шага в quest.

Правила целостности:

- `reward_limit` обязателен и положителен для `first_n` и `top_n`;
- `competition_closes_at` обязателен для `top_n`;
- `ranking_metric` обязателен для `top_n`;
- quest не может ссылаться сам на себя;
- связь с quest проверяется сервером: родительская запись должна иметь `activity_type = 'quest'`;
- денежные суммы Core и Wallet остаются отдельными полями и не смешиваются.

### 4.2 `public.user_challenges`

Добавить поля:

- `reward_status`: `pending`, `awarded`, `not_awarded`, `not_applicable`;
- `completed_at`;
- `completion_score`;
- `award_rank`.

Текущие статусы участия `accepted`, `completed`, `declined`, `failed` сохранить. `completed` означает выполнение условий, а не обязательно получение награды.

Для аудита и идемпотентности добавить отдельные allocation-записи или эквивалентный серверный журнал, обеспечивающий:

- уникальность распределения для одного `user_challenge`;
- уникальность одного конкурсного места;
- повторяемость финализации без повторной выплаты;
- связь с reward ledger и исходным challenge.

## 5. Серверная логика

Существующий flow `accept` сохраняется. Проверка выполнения должна передавать результат в единую серверную settlement-логику:

- `guaranteed` — проверить условия и сразу начислить reward;
- `first_n` — проверить условия, атомарно занять место и начислить reward только при успешном занятии;
- `top_n` — проверить условия, сохранить score и completion, оставить reward в `pending` до дедлайна.

Финализация `top_n` выполняется только доверенным серверным процессом после `competition_closes_at`. Публичный пользовательский endpoint не должен позволять самостоятельно назначать score, rank или award status.

Повторный `check`, повторный callback и повторная финализация должны быть безопасными и не создавать двойной reward.

## 6. API и UI

`GET /api/challenges` должен дополнительно возвращать:

- `activity_type`;
- `reward_mode`;
- `reward_limit`;
- `competition_closes_at`;
- `ranking_metric` или безопасное пользовательское описание критерия;
- `reward_status` текущего пользователя;
- `completion_score` и `award_rank`, если они доступны;
- остаток мест для `first_n`, если его можно безопасно показать.

В UI:

- mission показывает: «награда гарантирована при выполнении»;
- challenge показывает: «первые N» или «лучшие N»;
- top-N challenge показывает, что результат будет определён после окончания конкурса;
- quest показывает шаги и общий прогресс;
- completed, pending и not awarded отображаются раздельно;
- тексты не должны обещать награду там, где она зависит от места в конкурсе.

## 7. Совместимость

Все существующие активные записи при первой миграции получают:

- `activity_type = 'mission'`;
- `reward_mode = 'guaranteed'`.

Текущие записи `user_challenges`, completion snapshots, Core/Wallet reward fields, ledger и существующие verification logic сохраняются.

Таблица `challenges` не переименовывается. Уже применённые Supabase migrations не редактируются: любые изменения выполняются отдельной forward migration.

Системное авторство остаётся единственным способом создания новых catalog activities. Пользовательские personal tasks и командные задачи не получают автоматически права начислять Core или Wallet.

## 8. Этапы реализации

1. Добавить forward migration для новых полей, ограничений и allocation-аудита.
2. Обновить database types и серверный `/api/challenges`.
3. Вынести распределение guaranteed/first-N/top-N в идемпотентную серверную функцию.
4. Обновить `check`, progress и completion UI, не ломая текущие guaranteed challenges.
5. Добавить новые редакционные записи для каждого типа и проверить их eligibility.
6. Обновить каталог и пользовательские тексты после появления реальных примеров.

Эта задача является планом. В рамках документа не выполняются миграции, изменения Supabase, изменения кода или добавление карточек в канбан.

## 9. Тестирование и критерии приёмки

### Детерминированные тесты

- legacy challenge без новых полей продолжает работать как guaranteed mission;
- `first_n` с лимитом 1 выдаёт награду только одному пользователю при конкурентных запросах;
- `top_n` не выплачивает reward до дедлайна;
- после дедлайна `top_n` выбирает ровно `N` пользователей;
- одинаковый score разрешается по более раннему серверному completion;
- повторный check и повторная финализация идемпотентны;
- completed с `not_awarded` не отображается как выплаченная награда;
- quest не создаёт двойную выплату за дочерние шаги;
- local tasks и team tasks не становятся публичными challenge records.

### Authenticated QA

Проверить отдельными тестовыми аккаунтами:

1. гарантированную mission;
2. first-N challenge с лимитом 1;
3. top-N challenge с одинаковым score;
4. quest с несколькими шагами;
5. отсутствие утечки личных tasks и командного контекста.

### Проектные проверки

После реализации выполнить `pnpm exec tsc --noEmit`, `pnpm lint`, `pnpm build` и `git diff --check`, затем провести одну ограниченную визуальную проверку Challenges.

## 10. Границы и экономические допущения

- Общий prize pool не входит в MVP.
- Конкурсная награда ограничивается серверным `reward_limit` и не может выплачиваться повторно.
- Core и Wallet остаются разными счетами.
- Challenge reward не является внешней выручкой, обеспечением или доказательством ликвидности.
- Системные награды должны рассматриваться как отдельное обязательство с явно заданными параметрами и лимитом.
