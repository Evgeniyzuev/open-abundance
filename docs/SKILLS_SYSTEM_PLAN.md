# Skills System Plan

Статус: канонический продуктовый план системы навыков, обновлён 2026-08-08. Текущий automatic-checks-first срез включает L1–L10 для referral, public post и team fact. Оперативный порядок задаёт только `MASTER_KANBAN.md`.

## 1. Продуктовый контракт

`Skill Passport` показывает измеримые способности пользователя и следующий полезный шаг. Это не самодекларация, не сертификат о просмотре материала и не замена Core Level.

Основные правила:

- уровень навыка повышается только по проверяемому результату или наблюдаемой продуктовой метрике;
- первые уровни считаются автоматически сервером по тем же фактам, что и челленджи;
- `effective_skill_level = min(earned_skill_level, core_level)`;
- рост Core Level может раскрыть уже заработанный уровень, но сам по себе не создаёт новый навык;
- Skill Passport не принимает числовые значения от клиента как доказательство;
- навыки, Trust events и финансовый ledger хранятся раздельно;
- сертификаты и ручная механика review не являются частью текущего MVP.

## 3. Автоматические уровни

У каждого активного правила есть:

- `verification_logic` — тип серверной проверки;
- `threshold` — числовой порог;
- `requirements` — локализованное объяснение пользователю;
- `metadata` — машинные параметры и источник метрики.

Текущие типы логики:

- `referral_count` — строки `referral_edges`, где пользователь является referrer;
- `public_post_count` — опубликованные public-материалы пользователя без soft delete;
- `team_member_count` — активные `team_memberships`, где пользователь является leader;
- `team_contact_count` — активные системные team-контакты;
- `challenge_completion_count` — завершённые server-backed challenge snapshots.

Один server-side refresh пересчитывает текущие значения, записывает snapshot в `user_skills` и монотонно повышает `earned_skill_level`. Уменьшение уже заработанного уровня не выполняется автоматически: исправления аномальных данных остаются отдельной операторской процедурой.

## 4. Данные

Текущий MVP использует только три сущности:

- `skills` — каталог навыков, описание и learning path;
- `skill_level_rules` — измеримые правила уровней;
- `user_skills` — заработанный уровень, статус, время последней проверки и snapshot значений.

Отдельные `submissions`, `evidence`, human-review requests/decisions, progress-event ledger и `peer_points` в текущую миграцию не входят. Это предотвращает появление очереди ручных действий до того, как продукт определит их пользу и capacity.

## 5. Текущий vertical slice

Skill Passport в профиле:

1. вызывает серверный refresh;
2. показывает текущий уровень навыка рядом с названием;
3. показывает краткое описание и компактный прогресс к следующему уровню;
4. позволяет повторить проверку после действия пользователя;
5. не позволяет вручную подменить значение счётчика или отправить evidence.

Текущая реализация покрывает автоматические L1–L10 для referral, public content и team membership. `software_creation` остаётся в долгосрочном каталоге до определения честного наблюдаемого сигнала; ручной code-review flow для него не запускается.

## 7. Метрики и decision gates

Сейчас измеряются:

- доля пользователей, у которых refresh находит прогресс;
- completion rate каждого L1;
- время от продуктового действия до появления нового уровня;
- доля проверок с устаревшим snapshot;
- переход из полученного навыка к полезной задаче.

До добавления новых уровней нужно проверить:

- что источник метрики server-authoritative и не зависит от клиентского ввода;
- что порог достаточно сложен для полезного сигнала, но достижим в пилоте;
- что повторный refresh идемпотентен;
- что private и удалённые данные не попадают в публичный Skill Passport.

## 8. Отложено на неопределённое будущее

Следующие идеи сознательно не входят в execution queue и не имеют срока запуска:

- `skill_submissions` и `skill_evidence`;
- peer-review requests/decisions и reviewer pools;
- `peer_point` ledger, цена, возврат и рынок review;
- ручной `software_creation` L1 с rubric и rework;
- сертификаты, поручительство и влияние skill verdict на Trust;
- AI-matching reviewers и автоматические reviewer-награды.

Возвращаться к ним можно только отдельным decision-complete планом после подтверждения, что автоматических сигналов недостаточно.

## 9. Acceptance criteria текущего среза

- миграция создаёт только `skills`, `skill_level_rules` и `user_skills`;
- refresh выполняется server-side и читает существующие referral/content/team facts;
- клиент получает current value, threshold и passed status;
- earned level не повышается от payload клиента;
- effective level ограничен Core;
- в UI отсутствуют submission/evidence/review forms и очередь;
- remote migration и User QA фиксируются в Kanban отдельными внешними шагами.
