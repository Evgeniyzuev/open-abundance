# Языки: оценка текущей системы и план добавления zh, hi, es, ar

Статус: 2026-10-18. Этап A (основа) выполнен в коде локально, не закоммичен: `lib/locales.ts` (реестр языков, `normalizeLocale`, `pick`, `localeDirection`, `intlLocale`), `AppLocale` вместо `"ru" | "en"` в 20 файлах, загрузчики словарей в `lib/i18n.ts`, `dir` на `<html>`, `/api/user/locale` проверяет по реестру, скрипт `pnpm test:i18n`, миграция `20261018140000_profile_locale_any_code.sql` (**не применена к remote**; код от неё не зависит, пока языков только два). Этап C (испанский) начат: `lib/messages/es.ts`, 377 ключей уровня 1 из 2693 (навигация, Today, желания, задачи, уведомления, внешний вид, никнейм); остальное показывается по-английски. В реестре `es` помечен `complete: false` и грузится вместе с английским словарём. Выбор языка в «Внешний вид» строится из реестра (родные названия). Юридические тексты остаются ru/en (`toLegalLocale`), пуши и напоминания для `es` пока идут по-английски. Тип `Localized<T>` (`en` обязателен, остальные языки по желанию) и `pick()` заменили индексацию `obj[locale]` в 14 файлах: проверка типов теперь сама показывает места, где язык не учтён. Этап B (сквозной путь) сделан для зарегистрированных языков: выбор в онбординге (`ru`, `en`, `es`) переходит в профиль и приложение, `zh` и `hi` пока переходят в английский; гость без явного выбора продолжает на языке онбординга. Остальные этапы не начаты.

**Правило запасного английского (принято):** английский — базовый язык. Нет ключа, нет перевода, нет поля `{код: текст}` — показывается английский, и только в крайнем случае сам ключ. Язык, у которого нет всех ключей, помечается в реестре `complete: false`, и вместе с ним грузится английский словарь; у полных языков (`ru`) английский не грузится лишний раз. Переводы можно делать частично: сначала интерфейс и то, что не вызывает вопросов. Очередь и статусы ведутся только в [MASTER_KANBAN.md](MASTER_KANBAN.md). Дополняет [LANGUAGE_CONTEXT_PLAN.md](LANGUAGE_CONTEXT_PLAN.md).

## 1. Как устроено сейчас

- `lib/i18n.ts`: `AppLocale = "ru" | "en"`, свой словарь без библиотеки. `loadMessages(locale)` грузит один язык отдельным чанком (`lib/messages/ru.ts`, `en.ts`), `translate()` берёт ключ из выбранного словаря, затем из английского, затем показывает сам ключ. Подстановка `{name}` через `replaceAll`.
- Словарь: 2693 ключа, `en` 157 КБ, `ru` 260 КБ (кириллица занимает 2 байта; по сети около 58 КБ gzip). Расхождений ключей между `ru` и `en` сейчас нет (проверено скриптом).
- `UserProvider` отдаёт `locale`, `t`, `setLocale`, ставит `<html lang>`, сохраняет `user_profiles.default_locale` через `/api/user/locale`.
- Онбординг — отдельная система на 5 языков (`lib/onboardingContent.ts`: ru, en, zh, es, hi) с собственным ключом `openAbundanceOnboardingLocale`; после регистрации всё, кроме `ru`, превращается в `en`.
- Тексты вне словаря: JSON `{ en, ru }` в челленджах и навыках (`localizedText`), юридические документы (`lib/legal.ts`), база знаний Новы, `notificationCopy` в `app/api/notifications/route.ts`, тексты пушей (`metadata.copy.{ru,en}`), AI-промпты и запасные тексты в API.

## 2. Нужен ли рефакторинг

**Менять подход (библиотека i18next / next-intl / FormatJS) не нужно.** Загрузка одного языка, отсутствие рантайм-зависимостей и быстрый старт уже хороши; при шести языках каждый посетитель всё равно скачивает один словарь. Смена фреймворка дала бы риск и переписывание 2693 ключей без выигрыша в скорости.

**Нужен точечный рефакторинг, без него добавление языков хрупкое:**

| № | Проблема | Почему важно | Решение |
|---|---|---|---|
| 1 | `"ru" \| "en"` написано вручную в ~64 файлах, ещё ~84 проверок `locale === "ru"`, `normalizeLocale` превращает всё не-ru в en | Новый язык молча станет английским; каждое место надо найти руками | Один модуль `lib/locales.ts` — единственный источник: список языков с полями `code`, `nativeName`, `dir`, `intl` (тег для `Intl`), `status`. Тип `AppLocale` выводится из него. Функция `pick(locale, { ru, en, ... })` с английским как запасным вместо тернарников |
| 2 | `ru: Record<string, string>` — паритет ключей не проверяется типами | Новый язык легко оставить без части ключей, и пользователь увидит английский без предупреждения | Типизировать как `Record<MessageKey, string>` или `Partial<...>` с отдельным скриптом `pnpm test:i18n`: паритет ключей, одинаковые `{плейсхолдеры}`, нет пустых строк, длина кнопок |
| 3 | Список допустимых языков зашит в БД и API | `user_profiles.default_locale` ограничен `ru`/`en`, `/api/user/locale` отвергает остальное | Миграция: расширить ограничение, или хранить любой код из `lib/locales.ts` и проверять на сервере по этому же списку |
| 4 | Онбординг и приложение — две независимые системы языка | После регистрации китайский онбординг превращается в английское приложение, это разрыв пути | Сначала довести основной путь (раздел 5, этап B), затем объединить: онбординг берёт тексты из общих словарей, отдельный `onboardingContent` остаётся только для нового визуала |
| 5 | Множественное число: подстановка только `{count}` | В русском 3 формы, в арабском 6, в китайском и хинди разные правила | Использовать `Intl.PluralRules(locale)`; для таких ключей вариант `key.one`, `key.few`, `key.many`, `key.other`. Ввести по мере необходимости, а не для всех 2693 ключей сразу |
| 6 | Форматирование чисел и дат: `toLocaleString(locale…)` в ~20 местах, `createMoneyFormatter(locale…)` | Нужен правильный BCP 47 тег (`zh-CN`, `hi-IN`, `es-419`, `ar`) | Использовать `intl` из `lib/locales.ts`. Для арабского взять латинские цифры (`ar-u-nu-latn`): суммы Core, кошелька и TON-адреса не должны менять вид |
| 7 | Тексты вне словаря (пуши, API, `notificationCopy`, база Новы) | Каждое место привязано к двум языкам | Общее правило: `copy` — карта `код → текст`, запасной `en`. `claim_notification_deliveries` и `notificationCopy` выбирают язык получателя и откатываются на `en` |
| 8 | Один большой файл на язык | При 6 языках каждый посетитель загружает только свой, но редактировать 260 КБ файл неудобно | Пока не трогать. Разбивать по областям (`app`, `wallet`, `challenges`, …) только если словарь одного языка превысит ~150 КБ gzip или появятся конфликты правок |

Порядок: пункты 1–3 и 6 идут вместе до первого нового языка (они ничего не меняют для пользователя), остальное по мере надобности.

## 3. Языки: что именно добавляем

| Язык | Код | Решение |
|---|---|---|
| Китайский | `zh-Hans` (упрощённое письмо, стандартный мандарин; в онбординге сейчас `zh`) | Мандарин — основной разговорный стандарт, на письме — упрощённый. Традиционный (`zh-Hant`) для Тайваня и Гонконга — отдельно и позже. Сначала проверить, что приложение достижимо в Китае (платёжные и сетевые ограничения) — см. | Хинди | `hi` | Самый массовый в Индии, но не единственный; английский там тоже широко понимают. Начать с хинди, остальные языки Индии — по данным использования |
| Испанский | `es-419` (нейтральный латиноамериканский) | Большинство носителей в Америке. Без региональных форм (vosotros, местные идиомы); при необходимости позже отдельный `es-ES` |

## 4. Арабский и письмо справа налево

Да, проблемы есть, но они решаемы и в основном механические.

1. **Направление.** На `<html>` ставить `lang="ar" dir="rtl"` из `UserProvider` (рядом с уже существующим обновлением `lang`).
2. **Вёрстка на физических свойствах.** В `app/styles/*.css` около 195 объявлений `margin/padding-left/right`, `left:`, `right:`, `text-align: left/right`, `border-left/right` (больше всего в `screens.css` — 123, `core-and-reality.css` — 31, `creator-and-expedition.css` — 20; счёт по регулярному выражению, ориентировочный). Заменить на логические: `margin-inline-start`, `padding-inline-end`, `inset-inline-start`, `text-align: start`, `border-inline-start`. В LTR выглядит так же, поэтому миграцию можно делать заранее и безопасно, до появления арабского. Отдельно проверить встроенные `style={{ left, right, marginLeft … }}` в TSX (не подсчитаны).
3. **Иконки и жесты.** Стрелки «назад/вперёд», шевроны, прогресс-бары, свайпы и слайдеры нужно зеркалить; иконки логотипов, часов, галочек, плеера — нет. Для зеркалируемых — класс `.rtl-flip { [dir=rtl] & { transform: scaleX(-1) } }`.
4. **Смешанный текст.** Суммы, `Core`, адреса TON, хеши транзакций, e-mail, URL и числа остаются слева направо: оборачивать в `<bdi>` или `dir="ltr"`, иначе знаки и порядок «ломаются» в арабской строке.
5. **Шрифты.** Inter не содержит арабских, китайских и деванагари глифов. Использовать системные стеки на каждый язык (`font-family` по `:lang(ar)`, `:lang(zh)`, `:lang(hi)`), без загрузки веб-шрифтов: это быстрее и не раздувает страницу. Для хинди и арабского увеличить `line-height`, для китайского убрать `letter-spacing` и жёсткие `text-transform`.
6. **Длина строк.** Немецкий-подобного разрастания нет, но арабский и испанский длиннее английского на 20–30%, китайский заметно короче. Кнопки и вкладки не должны иметь фиксированную ширину в пикселях.
7. **Графики и карты.** Временные оси идут слева направо и в RTL (по международной практике); подписи осей и легенды локализуются, сами оси не зеркалятся.
8. **Проверка.** Один скриншот каждого главного экрана на `dir=rtl` в одном прогоне, без цикла по языкам и перезагрузок (правила проекта в `DEVELOPMENT_RULES.md`): Today, Wishes, Core, Wallet, Challenges, Profile.

## 5. План по этапам

| Этап | Что делаем | Результат |
|---|---|---|
| A. Основа (без видимых изменений) | `lib/locales.ts`; тип `AppLocale` из него; `pick()`; расширение БД и `/api/user/locale`; `Intl`-теги; запасной английский везде; `pnpm test:i18n` | Новый язык добавляется записью в список и файлом словаря |
| B. Основной путь | Слить онбординг и приложение: онбординг на zh/es/hi продолжается тем же языком до Today, желаний, расчёта Core, челленджей, уведомлений | Пользователь не «падает» в английский после регистрации |
| C. Испанский | Первый язык: он LTR, латиница, почти не меняет вёрстку; проверка длины строк | Пилотный язык нового набора |
| D. Логические CSS-свойства | Миграция physical → logical во всех стилях (безопасно для LTR) | Основа для арабского |
| E. Китайский и хинди | Системные шрифты, перенос строк, проверка в Китае/Индии | Два ещё LTR-языка |
| F. Арабский | `dir=rtl`, зеркальные иконки, `bdi` для чисел, скриншоты экранов | Первый RTL |

Покрытие по уровням (в каждый язык):

1. **Уровень 1 — основной путь:** онбординг, Today, желания, расчёт Core, челленджи, уведомления, пуши координатора.
2. **Уровень 2 — деньги и безопасность:** кошелёк, пополнение, вывод, P2P, тексты ошибок и предупреждений. Здесь машинного перевода недостаточно — нужна проверка носителем: неверный перевод суммы, комиссии или риска имеет финансовые последствия.
3. **Уровень 3 — остальное:** заметки, задачи, соцразделы, карта, настройки.

Пока уровень не переведён, показывается английский, а не ключ и не смесь с русским. Язык в списке выбора появляется с пометкой `beta`, пока не закрыт уровень 2.

## 6. Как переводить

1. **Глоссарий** на всех языках до начала: Core, Wish (желание), Challenge, Wallet, Total Core, Nova, лидерский бонус. Названия продукта (Core, Nova, Open Abundance) не переводятся.
2. **Черновик** переводит ИИ по партиям: ключ, исходный английский, контекст экрана и ограничение длины. Выход проверяет `pnpm test:i18n` (плейсхолдеры `{name}`, пустые значения, доли длины).
3. **Проверка носителем** обязательна для уровня 2, для юридических текстов, безопасности и согласий; для уровня 1 — выборочно, по реальным жалобам.
4. **Юридические документы** (`lib/legal.ts`): английский остаётся юридически главным; переводы показывать с пометкой «справочный перевод» и публиковать после проверки юристом.
5. **Нова.** Отвечает на языке пользователя; база знаний остаётся на английском и русском как источнике, а в промпт добавляется «ответь на языке пользователя». Тексты безопасности (`buildSafetyPayload`) и запасные ответы локализуются по тому же правилу, что и словарь.
6. **Контент в БД** (челленджи, навыки): JSON-поля `{ en, ru }` расширяются до карты `код → текст` с запасным `en`; отсутствие перевода не должно быть ошибкой.
7. **Пуши и уведомления:** `metadata.copy` — карта по кодам, `en` обязателен; язык получателя берётся из профиля.

## 7. Тестирование

- `pnpm test:i18n` (новый): паритет ключей относительно `en`, совпадение плейсхолдеров, пустые значения, допустимые коды в БД и API, наличие `dir` в `lib/locales.ts`.
- Детерминированные проверки перевода и форматирования (`Intl` для каждого языка) без навигации.
- Один скриншот на экран для RTL и для CJK/деванагари в одном прогоне; цикл по языкам с перезагрузками запрещён правилами проекта.
- Перед включением языка для всех: уровни 1–2 закрыты, на тестовом аккаунте пройдены регистрация → желание → расчёт Core → челлендж.

## 8. Что не проверено

Не подсчитаны встроенные стили в TSX (`left`, `right`, `marginLeft`) и не проверено, как сейчас обрабатываются формы множественного числа в русских строках (в словаре видна подстановка `{count}`, отдельных форм не найдено). Это входит в этап A.
